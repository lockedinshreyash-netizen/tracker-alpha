# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"LOCK IN JEE'27 Tracker" — a single-page React app for tracking daily study logs, syllabus progress, and question practice for JEE/NEET 2027 aspirants (India). Vite + React 19 + TypeScript, no test framework or linter configured.

## Commands

```bash
npm run dev      # start Vite dev server on port 3000 (host 0.0.0.0)
npm run build    # production build
npm run preview  # preview production build
```

There are no test, lint, or typecheck scripts defined in `package.json`. `tsconfig.json` has `noEmit: true`, so `npx tsc --noEmit` can be used to typecheck manually if needed.

**`tsc` does not check React component props here.** `tsconfig.json` sets neither `esModuleInterop` nor `allowSyntheticDefaultImports`, so the default `import React from 'react'` resolves to `any`, every `React.FC<Props>` is therefore `any`, and JSX prop mismatches — wrong name, wrong type, missing required prop — pass silently. Verify prop wiring by reading it or by running the app; do not trust a clean `tsc` on that specific point. Enabling `esModuleInterop` would restore the checking but will surface pre-existing errors across the codebase.

Environment variable `GEMINI_API_KEY` is read via `vite.config.ts` and exposed as `process.env.API_KEY` / `process.env.GEMINI_API_KEY` (not currently referenced elsewhere in the code).

## Architecture

- **Monolithic `App.tsx`** (~1800 lines) contains the root `App` component plus most tab components defined inline as local consts: `AuthModal`, `Header`, `Navbar`, `TaskSection`, `SyllabusTab`, `MonthlyHeatmap`, `StreakTab`, `ReviewTab`, `TodayTab`. When making changes, search within this file rather than assuming separate component files exist.
- **Separate top-level components**: `Sidebar.tsx`, `LandingPage.tsx`, `OnboardingTour.tsx`, and the `landing/` (Hero/Features/Stats/FinalCta sections) and `questions/` (Questions tab + its subsections) directories.
- **`review/`** holds chart components (`QuestionsBarChart`, `QuestionsHeatmap`) used by `ReviewTab`.
- **State shape** is centralized in `types.ts` (`AppState`), covering logs, syllabus progress, tasks, timer, lock-in mode, question tracking, and theme. `constants.tsx` holds static config: syllabus chapter lists per class/subject, status colors/labels, exam-preference helpers (`getActiveSubjects`, `getCoreSubjects`, `getCoreQSubjects` switch behavior between JEE and NEET), and exam countdown target dates.
- **`utils.ts`** has pure functions operating on `AppState`/`DailyLog[]`: IST date handling (`getISTDateString` — all dates are computed in Asia/Kolkata timezone, not local time), streak calculation, 7-day stats, subject distribution, and the "Lock-In Score" composite metric (consistency 30% + volume 30% + syllabus progress 10% + quality 30%, minus a distraction penalty).

### Persistence & sync model (in `App.tsx`)

- Local-first: full `AppState` is persisted to `localStorage` under key `locked_in_state_v2` on every state change.
- Optional cloud sync via Supabase (`@supabase/supabase-js`), table `user_profiles` (columns: `id`, `state` jsonb, `updated_at`). The Supabase URL/anon key are hardcoded in `App.tsx`.
- Conflict resolution uses a `lastUpdated` timestamp on `AppState`: on initial sync, whichever of local/remote has the newer `lastUpdated` wins wholesale, except when local is newer, in which case `logs`/`tasks` are merged by `id` to avoid resurrecting deletions while keeping unique entries from both sides. UI-only fields (`lastUsedTab`, `theme`) always stay local.
- A Supabase Realtime channel (`profile_changes_${user.id}`) listens for `UPDATE` on `user_profiles` and applies remote state locally if its `lastUpdated` is newer, guarded by a `preventSyncOnUpdate` ref to avoid sync feedback loops.
- `triggerSync` upserts state to Supabase, debounced via `isSyncingRef`/`pendingSyncRef` so overlapping writes queue rather than race.
- Auth (email/password) is handled through `AuthModal` and `supabase.auth`; signing out clears all `sb-*` and the `locked_in_state_v2` localStorage keys and resets to `DEFAULT_STATE`.

### Streak rewards (`rewards/`)

- Milestones live in `rewards/catalog.ts` (`REWARDS`) — day 30 wallpaper pack, day 100 in-app book, day 365 physical hamper. Adding a tier is one entry there, provided its `kind` already has a way to be opened. Nothing else hardcodes a milestone.
- `rewards/engine.ts` is pure: `evaluate` re-derives unlocks from logs on every `state.logs` change (returns the *same* object when nothing changed, so the effect settles in one pass). Because it runs on mount, users with pre-existing streaks get their tiers backfilled.
- **Unlocks come from the longest run in the history, not the live streak.** `evaluate` uses `longestStreak`/`longestVerifiedStreak` (`utils.ts`) over all logs, so a month that ended in March still pays out, and a backfilled month counts. The earlier rule read `calculateStreak`, which only sees the run reaching today — a completed 30-day run that broke before the vault was next opened was never rewarded at all.
- **Progress is measured by the live streak.** `rewardProgress(rewards, streak, verifiedStreak)` — the days-to-go line has to answer "what does one more day buy me". Driving it off the high-water mark froze the whole vault for anyone rebuilding after a break (day 8 of a new run, best of 12 → "18 days to go", unchanged for four days running, directly under a card reading "Current streak: 8"). The stored best is shown beside the bar as `best N` when it beats the run in progress, and nothing else.
- **Unlocks are permanent and monotone.** Breaking a streak never revokes one. `RewardsState` stores `bestStreak`/`bestVerifiedStreak` high-water marks so deleting old logs cannot take a reward back either. That one-way property is why `mergeRewards` unions rewards on sync instead of letting last-write-wins drop a tier — it is applied in all three merge paths in `App.tsx` (cloud-newer, local-newer, realtime).
- Rewards with real cost behind them (`requiresVerified: true` — book, hamper) count only the **verified streak**: consecutive days with a `timer`/`pomodoro` log, via `calculateVerifiedStreak` in `utils.ts`. Manual backfills keep the visible streak alive but cannot mint a year of study in a for-loop. Same stance the leaderboard takes on `LogSource`.
- UI: `RewardsVault` (in `StreakTab`) shows locked tiers too — a prize you cannot see is not a reason to log tomorrow. `UnlockModal` fires once per reward, oldest un-shown first, gated on `acknowledged`.
- Wallpapers (`rewards/wallpapers.ts`) ship no image assets — every design is layered CSS, plus SVG data URIs generated at module init by `starfield()` (a seeded PRNG placing individual stars; tiled `radial-gradient` dots were tried first and always read as graph paper). `rewards/WallpaperLayer.tsx` paints both the fixed full-page layer in `App.tsx` and the picker swatches, so a preview is exactly what gets applied.
- The Aurora wallpaper is animated, which a CSS `background` cannot be — it renders real elements: `AURORA_CURTAINS` (masked ribbons of hairline "rays" over a luminous sheet) and `AURORA_GLOWS` (unmasked, heavily blurred ambient spill so the light falls off across the page instead of stopping at the mask). Motion lives in `index.css` (`aurora-drift`/`aurora-glow`/`aurora-shimmer`/`aurora-breathe`) and is disabled under `prefers-reduced-motion`. Per-element `animationDuration` must list one value **per keyframe animation** — a single value silently applies to all of them and locks the cycles together.
- Two things constrain every wallpaper: they sit behind the header, so peak brightness has to leave the countdown text readable; and the same CSS paints a 64px swatch, so no viewport units.
- The day-100 book text is `content/book.ts` — **currently a scaffold** with `complete: false`. Replace `BOOK.chapters` with the manuscript and flip the flag; the reader, vault and progress all read from there. It is bundled rather than fetched so it works offline.
- The hamper claim is deliberately a `mailto:`, not a form. The app never collects a postal address — most users are minors, and shipping details in a synced jsonb blob is a liability, not a feature.

### Scheduling (`schedule/`)

- The **Plan** tab, and it schedules the *whole* day, not only study. `schedule/schedule.ts` is pure and React-free (same contract as `today/pomodoro.ts`); `PlanTab.tsx` is a zero-logic container over `DateStrip`, `DayTimeline`, `AdherenceSection` and `TemplateSection`, taking a narrow slice plus narrow callbacks like `questions/QuestionsTab.tsx` — never `AppState` or `setState`.
- **`BlockKind` is the primary axis, not `Subject`.** `schedule/colors.ts` holds `ACTIVITIES`, the single registry of what a block can be (study/revision/test, then class/sleep/meal/gym/break/travel/other) along with its label and a sensible default time and length for one-tap adding. `ScheduleBlock.subject` is therefore **optional** — sleep has no subject, and giving it a phantom `General` would drag it into the adherence maths. `countsAsStudy(kind)` is the one predicate that decides what is measured; `blockStyle`/`blockTitle` decide how a block reads. Study blocks are coloured by subject, life blocks by kind and deliberately low-chroma, so the work stays the thing your eye lands on.
- Times are shown as **12-hour with AM/PM** (`formatClock` "6:30 AM", `formatHour` "6 AM" for the axis gutter, `formatRange` writing the meridiem once when both ends share it: "6:00 – 7:30 AM" but "11:00 AM – 1:00 PM"). `DayMinute` stays 24-hour arithmetic from 04:00; the meridiem is presentation only.
- The editor asks **what it is first**, and only then shows the fields that kind actually has — subject and chapter for study, a free-text name for everything else. Switching families clears the detail that no longer applies, so a block cannot keep a subject it stopped having. Two rules keep the sheet from being a wall of chips: **colour carries the selection where colour means something** (a kind or subject chip wears its own colour when chosen, so the row doubles as the legend and the header previews the block you are about to make; durations and repeat keep the accent), and **time is typed, not stepped** — start and end are real `<input type="time">`, so 6:45 is one entry rather than five taps, the OS supplies the phone keyboard, and the duration row is a shortcut rather than the only route. `toClockValue`/`fromClockValue` bridge the 04:00 axis: typing an end of 1:30 on an 11 PM block gives 2h 30m, because 1:30 is simply later on that axis. The footer is `sticky bottom-0` — the button that commits the block should never be somewhere you scroll to find.
- The clash warning **names what you collide with** ("Overlaps Coaching"), not how many — a count made you close the sheet to find out which.
- A block cannot straddle the 04:00 rollover, so sleep entered as 11 PM–7 AM clamps to **11 PM – 4 AM** and the editor says so; the remainder is a second block on the next day. Splitting it automatically would give the user two halves that drag and delete independently, which is worse than the honest clamp.
- **`DayMinute` is minutes since 04:00 IST, not since midnight.** Minute 0 is 04:00, 1200 is midnight, 1439 is 03:59 the next morning. Storing wall-clock minutes instead would make a 23:00–01:00 block wrap, and every one of overlap detection, sorting, layout, drag-clamping and hit-testing would need a special case. `start + durationMins <= 1440` is a hard clamp everywhere (`clampBlock`) — a block may not straddle the rollover, or its hours would land on two study days and be unfalsifiable against `logs`. The grid draws a labelled `MIDNIGHT` divider at 1200 so the wrap is legible.
- **Recurrence is rules plus per-date overrides, never materialized rows.** `TemplateRule` has `days`/`from`/`until`; `materializeDay(schedule, date)` derives instances on read and gives each the synthetic id `` `${ruleId}@${date}` `` — the same key a `BlockOverride` uses, so an instance has a stable identity without anything being written for days you never touched. Writing seven rows a week would grow the synced jsonb blob without bound and would need a nightly job that has nowhere to run.
- **Repeat is a first-class control in the editor, not a hidden action.** `RepeatMode` is `none | daily | weekly | custom`; `daily` is simply a `TemplateRule` whose `days` is all seven, so nothing in the model special-cases it. `custom` is the days the three buttons cannot name (Mon–Fri, Tue/Thu) — `repeatOf` used to read any sub-seven rule as `weekly`, so opening a Mon–Fri coaching block on a Tuesday and pressing Save silently deleted the other four days; `daysForRepeat` now takes the rule's current `days` and hands them straight back for that mode. The choice is applied by `saveDraft` alongside every other field, which handles all six transitions (new/existing × one-off/repeating). It replaced a buried "Repeat weekly" link that always wrote `days: [today's weekday]` — users read "repeat", looked at tomorrow, saw nothing, and reasonably concluded it was broken. Turning a repeat back off deletes the rule **and writes a one-off for the day you are on**: the user asked for one block, not for none.
- **Deleting a repeating block asks which one you mean.** "Delete from today" writes a skip override; "Delete from every day" deletes the rule. A single "Delete" removes the wrong one for half the people.
- **Editing a rule closes it and opens a new one** (`updateRule` in `App.tsx`: old rule's `until` = yesterday, a new rule `from` today), and `deleteRule` sets `until` rather than removing the row. Editing in place would move the slot on days already spent, so last Monday's adherence would silently be re-measured against a plan that did not exist when it was lived. A rule starting today or later has no such history and really is edited/removed outright. **The reopened rule takes its still-future overrides with it** — they are keyed by rule id, so re-opening under a new id used to orphan every one: a day skipped next week came back, a day moved next week jumped. Overrides on days already lived stay with the closed rule, which is the whole point of closing it.
- **Dragging a repeating block asks which one you mean too** (`ScopePrompt`, same stance as delete). A drag of a rule instance is ambiguous between "this Tuesday" and "every Tuesday"; `DayTimeline` still commits once on release, but `PlanTab` holds the geometry in `pendingMove` and writes nothing until the user answers. It is one tick box — "Move every day?", **ticked by default**, because you dragged the block a repeat put there and so most of the time you meant the repeat — over a single Move it button. Ticked calls `updateRule` with `clearOverrideOn: date`, so the day you dragged is not left as the one exception to the change you just applied to every day; unticked writes an override for that date (`updateBlock` routes on whether the id contains `@`). Answering silently — always "this day only" — is what made a plan look right today and land in overlapping pieces tomorrow: a student who built a repeating skeleton and then tidied it by dragging saw every block snap back to its pre-drag time the next morning. While the prompt is up the block is drawn where it was dropped; cancelling reverts it, since nothing was written. `normalizeSchedule` (`state.ts`) drops overrides whose rule is gone, which is what keeps that array bounded.
- A rule created from the grid starts on the **day being planned**, not unconditionally today (`addRule` takes an optional `from`, clamped to no earlier than today) — turning tomorrow's block into a repeat must not also drop it onto the day you are standing in.
- **A gesture never touches `AppState`.** Every state change writes localStorage and fires `triggerSync`, so committing per frame would mean ~60 Supabase upserts per drag. `DayTimeline` keeps live geometry in a `preview` state plus a `dragRef`, and calls the mutator exactly once on release. Pointer Events, not HTML5 drag-and-drop (no touch support, no resize); `pointermove`/`up` are bound to **window**, because `setPointerCapture` routes captured events back to the element that claimed them and a handler anywhere else would never fire. A `ref`-only gesture cannot wake an effect, hence the `gesture` state whose only job is attaching those listeners. `pointerup` after a real drag sets `suppressClickRef` so the trailing click does not open the editor on the block just moved.
- All block geometry is **inline `style`**, never Tailwind. Tailwind here is the CDN script with no config, so `h-[${n}px]` in a template literal compiles to nothing. `touchAction: 'none'` on cards and handles is what makes touch dragging work at all; the 56px hour gutter stays scrollable so the grid can still be panned on a phone.
- Overlaps are allowed, never blocked — `layoutDay` splits clashing blocks into side-by-side lanes and the editor warns without refusing. A student double-booked at 19:00 is information; refusing the drop reads as the app being broken.
- **Past days are read-only.** Editing yesterday's plan after the fact would falsify its adherence.
- **Only study is graded.** `computeAdherence` filters to `countsAsStudy(kind) && !!subject` — you do not get marked down on dinner, and a block with no subject could never be matched to a log, which carries one.
- **Adherence is two-tier, and the UI says which.** `DailyLog` has a date, a subject and hours but **no start time**, so per-block truth exists only when the app was watching: `startBlock` stamps `TimerState.blockId`/`chapter`, `handleStopTimer` passes them to `logStudy`, and they land on the log (this is also why `logStudy` gained trailing optional `chapter`/`blockId` params, and why `engageRecommendation` now carries `rec.chapter` — `hoursOnChapter` in `recommend.ts` had been reading a field nothing ever wrote). Everything else is allocated by subject, **earliest block first** — the charitable reading that still leaves a late block correctly marked skipped — and the leftover is `offPlanMins`. Blocks of kind `break`/`fixed` are commitments and never count as planned study.
- **Subject colours are data; everything else is the user's.** `schedule/colors.ts` is the app's only subject colour map, and `SUBJECT_COLORS` is fixed — Physics is that blue on the grid, in the charts and on every device, and a subject you can recolour is a subject you can no longer read at a glance. Every non-study kind (`RECOLOURABLE`) is the user's to pick, from twelve presets or a native `<input type="color">`, in `PaletteSection` on the Plan tab; the choice lives in `state.schedule.colors` keyed by `BlockKind`. Defaults (`ACTIVITY_BASE`) are saturated on purpose — the old near-grey life palette kept the work in front but made the tab look like a spreadsheet, and study blocks already win by carrying a subject colour and a chapter name.
- **Every block colour is applied inline, never as a Tailwind class.** `BlockStyle` now holds CSS colour strings rather than class names, because a user-picked hex cannot become a class here (CDN Tailwind, no JIT over template literals — `bg-[${hex}]` compiles to nothing). Activity styles are computed from one hex by `derive`: translucent `rgba` fill and border so a block reads as tinted glass on either ground, and text mixed toward white on dark / black on light so a saturated pick stays legible. Subject values stay spelled out literally so they render byte-identical to before.
- A stored colour ends up in an inline `style`, so `normalizeSchedule` validates it against `HEX_RE` (`#rrggbb`, nothing else) and drops keys for study kinds outright. `mergeSchedule` merges the colour maps key-by-key with local winning — they are settings, not rows, so there is nothing to lose by keeping the other device's picks.
- The accent `#E10600` is deliberately absent from both palettes and from the preset list — that belongs to the now-line and to actions.
- **Styling follows `questions/`, not `today/`**: card `p-8 md:p-10 rounded-xl border` with `bg-[#111114] border-white/[0.06]` dark / `bg-white border-zinc-100 shadow-sm` light; section headings are small eyebrows (`text-[10px] font-bold uppercase tracking-[0.06em]` in `text-zinc-500`/`text-zinc-400`), not display type; muted text uses the zinc scale rather than white/black alphas.
- `mergeSchedule` runs in the **local-newer sync path only**, exactly like the by-id merges of `logs`/`tasks`. A union in the realtime or cloud-newer paths would look kinder and be wrong: a block deleted on the phone has to reach the laptop, and a device that unions can never be told something is gone.

### Shareable stats (`share/`)

- Three cards — **Daily** (near-black), **Weekly** (warm cream), **Monthly** (deep forest green) — rendered as PNGs from real logged data and pushed out through the OS share sheet. Reached from a `ShareButton` on **Streak** (opens on the week) and **Today** (opens on the day).
- **Canvas 2D, drawn imperatively, zero dependencies.** The two alternatives both fail on this stack: a DOM screenshot (`html2canvas`) inherits the browser's rasterisation and reimplements CSS badly, and an SVG loaded into an `<img>` **cannot load an external font** — every line of type would silently fall back unless the woff2 were base64'd into the string. Canvas gives exact pixel control at any resolution, and **fonts never taint a canvas**, so Satoshi coming from a third-party CDN is not a CORS problem.
- **The preview *is* the canvas.** `useCardImage` hands `ShareModal` the same `HTMLCanvasElement` that produced the blob, CSS-scaled. There is no second HTML rendering of a card to drift, so what the user approves is byte-for-byte what leaves the device. The corollary: the node holding it must have **no React children** — React and `replaceChildren` cannot both own a parent, and when they try React throws `NotFoundError` on the child it no longer finds. The loading and error states are siblings for that reason.
- **`navigator.share` needs transient user activation, and an `await` spends it.** Rendering or encoding inside the click handler makes iOS Safari throw `NotAllowedError`. The blob is therefore encoded alongside the preview and `onPrimary` is deliberately not `async`.
- **There are no Instagram or WhatsApp buttons, and there must not be.** Neither is reachable from a web page: Instagram's Stories path needs a native app with a registered Facebook App ID writing to the iOS pasteboard, and `wa.me`/`whatsapp://` carry text only. The OS sheet lists both and is the only real integration that exists. Capability is probed with an actual one-byte `File` through `navigator.canShare` — never a UA check, because desktop Firefox and Chrome-on-Linux have `navigator.share` and reject files. The one place a UA check *is* correct is `saveCard`: iOS Safari ignores `<a download>` for blob URLs, which is a rendering quirk with no feature to detect, so it opens a tab and the UI says to long-press.
- **`share/stats.ts` is pure and is the only place arithmetic happens.** `render/*` receives labels and rounded numbers and asks the data no questions — a canvas layout that also computes is one nobody can adjust.
- **Counting stops at today; drawing does not.** `lived()` clamps every aggregation to days that have happened, so a clock-skewed device cannot produce `27/07 DAYS ACTIVE`. The week still draws seven bars and the month still draws all its dots — the empty tail is the period still being written. The bars specifically are built from the *counted* range: a chart summing to visibly more than the hero above it is the one contradiction a shared card cannot survive.
- **Comparisons are like-for-like.** An in-progress month measured against a *complete* previous month reads as a 70% collapse on the 7th, which is arithmetically true and useless. The previous period is read over the same number of elapsed days, clamped to its own length so a 31-day month never reaches past the end of a 28-day one. No previous period, or a previous period of zero, drops the slot entirely — `0%` claims a flat week that never happened and `—` looks like a bug.
- **The second metric is a fallback chain, not a field**: tasks → questions → sessions (daily stops before sessions, which it already prints). `Task.completedAt` only exists going forward, so an account with months of history can have no dated completions at all; the label travels with the value so the card can never announce the wrong noun.
- **Type is Satoshi + Playfair only** — the app's own faces. `fonts.ts` asks for **900, not 800**: the mirror serves 300/400/500/700/900, so `fonts.check('800 …')` answers *true* for a weight that does not exist and the verification would be meaningless. The Monthly hero is Playfair 700 — the reference's monthly figure is a serif, and it gives that card its own identity without a new colour or layout. Every hero goes through `fit()`, which is also the entire font-fallback strategy: a wider fallback face fits by the same mechanism instead of running off the card.
- Three **real compositions** in `render/format.ts` (4:5 / 9:16 / 1:1), not one scaled three ways — 9:16 redistributes the vertical space and carries deep safe margins so Instagram's chrome never lands on the work. Exported at 2× (2160px wide).
- `#E10600` appears on **no card**. The accent belongs to actions and to the now-line, the same reservation `schedule/colors.ts` makes. The `@lockedinshreyash` invitation lives in the modal and never on the artifact.
- Phrase selection (`phrases.ts`) is **deterministic** on the stat state — a caption that reshuffles per render turns the artifact into a slot machine, and the user notices the second time they open the sheet.
- **The app's only lazy boundary.** `React.lazy` on `ShareModal` keeps the renderer out of the main bundle (~23 kB separate chunk). Nothing in the share flow writes `AppState`, so no card ever fires `triggerSync`.
- `share/DebugCards.tsx` is a dev-only contact sheet at **`?share=debug`** — every period × every format × seven fixtures (zero, first period, legacy tasks, extremes, February) on one page. Gated on `import.meta.env.DEV` and tree-shaken out of production. It is how the compositions get compared against the reference; "it renders" was never the bar.

### Task board (`board/`)

- The Today tab's task list is a **three-column board** — Todo → Doing → Done — replacing the old flat `TaskSection` grid. `board/board.ts` is pure and React-free (same contract as `schedule/schedule.ts`); `board/TaskBoard.tsx` is a zero-logic container taking a narrow slice plus narrow callbacks, like `questions/QuestionsTab.tsx`.
- **`completed` stays authoritative, `column` is written in lockstep.** `share/stats.ts` counts `completed && completedAt`, the voice grammar sets it, and every task saved before the board has nothing else. `moveCard` is the *single* code path that writes `completed`/`completedAt`/`column`, and `toggleTask` routes through it — otherwise the voice command and the board can disagree about the same card.
- `normalizeTasks` (`state.ts`) is new: there was no task normalizer before, and the board cannot tolerate a missing `column`. It derives one from `completed`, forces the two to agree when a sync merge produces a row where they don't, and backfills `order` per column by array position so a legacy list opens in the order it was written.
- **Ordering is a stored `order`, reindexed 0..n on every drop** — not fractional ranks. A board holds tens of cards, and a whole-column reindex also repairs the duplicate orders a sync union can leave behind. Sorting falls through to the id so two devices resolve ties identically.
- Drag copies `schedule/DayTimeline.tsx`'s discipline wholesale: **a gesture never touches `AppState`** (one commit on release, not ~60 upserts per drag), Pointer Events with listeners on `window`, a `gesture` state to wake the binding effect, a movement threshold, and `suppressClickRef` so the trailing click does not open the editor on the card just dropped. What differs is the arithmetic — a column/index hit test instead of pixels-to-minutes — so `board/useCardDrag.ts` is written fresh rather than extracted from a working gesture that has no columns in it.
- Two rules exist for a cheap phone: pointer moves are **coalesced into one `requestAnimationFrame`**, and **every rect is measured once at `pointerdown`** (`getBoundingClientRect` in a move handler forces synchronous layout every frame). The dragged card moves by `translate3d` only, with `will-change` on that one card and removed on release.
- **`React.memo` on the board is load-bearing, not decoration.** `today/TodayTab.tsx` runs a 100ms interval while a stopwatch is going, so the tab re-renders ten times a second through every session. The board's App-level mutators are therefore `useCallback([])`, and `activeSubjects` is memoised — `getActiveSubjects` returns a fresh array literal per call, and an unstable array there silently defeats memo on every child that receives it.
- Mobile is horizontal **scroll-snap** columns at ~82vw with edge autoscroll during a drag; three columns on a 375px screen is unusable. Done shows the most recent `DONE_VISIBLE` with a "+N earlier" expander — a Done column with 200 cards is a wall, and arriving in it is the point of the column.
- **Card colour is subject-tinted by default with a per-card hex override**, dispatched exactly like `blockStyle`: `taskStyle` reuses `derive` and `subjectStyle` from `schedule/colors.ts`. `SUBJECT_COLORS` stays fixed — the override is the user's own label, and it never rewrites what Physics-blue means elsewhere. `PRESET_COLORS` moved into `schedule/colors.ts` so the palette and the card picker share one list. Every colour is an inline `style`; CDN Tailwind compiles `bg-[${hex}]` to nothing.
- **Deadlines are a field on `Task`, not a separate entity.** `dueAt` is a study day; `dueMinute` is on the **study-day axis** (0 = 04:00), the same axis as `ScheduleBlock.start`, so `toClockValue`/`fromClockValue` bridge it to an `<input type="time">` with no new conversion code. Absent `dueMinute` means "use `ReminderPrefs.defaultMinute`", so moving that default moves every task that never asked for a time and none of the ones that did.
- The card's due label is **calm and deliberately not a countdown** — "DUE SUN", "DUE TOMORROW", and past it "OVERDUE" in the accent. A live shrinking countdown on every card is a pressure users tune out inside a week.
- **Task → plan link**: `ScheduleBlock`/`TemplateRule` carry an optional `taskId`, and `BlockEditor` offers a task picker on study kinds. `blockTitle(block, taskText)` takes the resolved text as an argument — `PlanTab` builds the map and passes it as **display text**, never writing it onto the block, because the editor reads `label` back off the block when it opens and would save a borrowed title as a real one. `normalizeSchedule(raw, knownTaskIds)` drops links to deleted tasks (App's load path is the one place with both halves in hand). Deliberately one-directional: finishing a block does not tick the task, because sitting down to work on something is not finishing it.
- Session history on Today is **collapsed by default** behind a header carrying the count and hours. Local `useState` — a disclosure preference is not data, and in `AppState` it would fire a Supabase upsert every time somebody opened it.

### Notifications (`notify/`) and reminders (`reminders/`)

- **The product rule moved and changed.** `leaderboard/notify.ts` used to open with an absolute law: a notification reports a race that is actually happening, or it is nothing. That rule now lives at the top of `notify/channels.ts` with its real boundary: **the app never invents a reason to interrupt you; it may hold you to something you wrote down yourself.** A deadline you typed on a date you chose is allowed to speak. "You haven't studied today" is still forbidden, and so is any digest, streak-at-risk warning or idle nudge. `leaderboard/notify.ts` keeps a race-scoped header pointing here.
- **One `showNotification` call site** (`notify/system.ts`), replacing two duplicate `new Notification` calls. It **prefers the service worker registration over the constructor** — that is a correctness fix, not a preference: Android Chrome throws on the constructor outright, so the Pomodoro bell had never once rung on a phone, the only device where a backgrounded bell matters.
- `notify/deliver.ts` routes one event to exactly one place: seen → dropped, visible tab → toast, hidden tab → system notification, closed app → push. Never two.
- `notify/toastBus.ts` is a **module-level bus, not a context**. Half the callers are not components (the Pomodoro bell fires from inside a `useCallback`, the reminder engine from a window handler), and a context whose value changes per toast would re-render every consumer under App's single `state` — a nine-second countdown paid for by the timeline and the heatmap. `ToastHost` is the only subscriber and renders `null` when empty, which is almost always. Auto-dismiss clocks **pause while the tab is hidden**, or a toast pushed just before a tab switch burns its nine seconds unseen — precisely the case `deliver` chose a toast for.
- `RaceToast` was migrated onto the bus. `questions/TodayQuestionsSection.tsx`'s pill and `voice/VoiceControl.tsx`'s flash were **deliberately left alone**: the first is a receipt positioned inside its own section (promoting it to a top-centre banner detaches it from the counter it confirms), and the second is a live transcript that updates many times a second. Three implementations, three reasons.
- `reminders/reminders.ts` is pure. Its central idea: **almost every cancellation is a filter, not an operation.** Ticking a task off, clearing its date, or deleting it all stop its reminder because the scan stops selecting it — there is no `cancel()` and therefore nowhere to forget to call it, which matters because tasks are mutated from App, three voice intents, the board and the sync merge.
- `Task.remindedKey` is **the fire key, not a boolean**. The key contains the due instant, so moving a deadline re-keys and re-arms it by itself. It rides the synced blob deliberately: a reminder fired on the laptop must not fire again on the phone.
- `reminders/useReminders.ts` is mounted at App root beside `usePomodoro`, for the reason that hook documents — an engine inside a tab component stops existing when the user opens another tab. It mirrors the same discipline: wall-clock derived, idempotent per fire key, `ready` gated on the initial cloud pull (a pull replaces `tasks` wholesale and would otherwise discard a `remindedKey` and double-fire), and a mount pass that **is** the catch-up-on-reopen path rather than separate code.
- **One timeout for the whole board**, armed at the earliest pending instant — not one per task. The 30s safety interval only runs when something is within the hour; a user whose next deadline is in December arms **nothing at all**.
- A reminder more than `STALE_REMINDER_MS` (12h) overdue is **marked silently and never shown** — telling somebody at 4am about a 4pm deadline is an accusation, not a service, and the card already reads OVERDUE. Past `MAX_BURST`, fires collapse into one line.
- **Never the same reminder twice**, via four independent mechanisms: `PUSH_LAG_MS` (90s) so an open app always fires first and deletes its own row; that row deletion; the IndexedDB ledger in `notify/seen.ts`, shared with `public/sw.js` (IndexedDB rather than `localStorage`, which does not exist in a service worker — the one context that most needs to ask); and the per-task `tag`, which makes even a true double-show replace rather than stack.
- **`public/sw.js` is push-only: no `fetch` handler and no caches.** A `fetch` handler sits in front of every request forever, and since the old worker lived at the repo root — which Vite does not copy into a build — production has never had one, so adding a caching worker would be a brand-new app-wide change to how every page loads. Offline caching is a separate decision about an app that already works. Registration is `/sw.js` with an explicit root scope; a relative `./sw.js` resolves against the *page*, so a deep link would register a narrower scope and pushes would never arrive.
- `reminders/publish.ts` is a **reconciler, not per-mutation calls** — the desired row set is a pure function of the tasks, so every cancellation falls out of the diff. Debounced, and skipped on an unchanged signature (`rewards/engine.ts`'s no-op contract applied to a network call). Dynamically imported, as is `notify/push.ts`: a user who never enables push downloads neither.
- `supabase/reminders.sql` holds two narrow tables, **deliberately not `user_profiles`**. The sender runs as the service role and bypasses RLS entirely, so if it read that jsonb blob it would be a cron job with unrestricted access to every user's private life, running every minute, forever. The client decides what is due and publishes only the two strings it wants read back to it. Same reasoning `leaderboard.sql` gives, with sharper stakes.
- The Edge Function **claims before sending** (`update … set sent_at where sent_at is null returning *`). The trade-off is stated in the code: claiming first can lose a reminder on a crash, sending first can duplicate one. The rule is "never twice" — a lost reminder is a disappointment, a duplicated one is why people turn notifications off.
- Deploy is user-run and documented in `supabase/functions/send-reminders/README.md`. The feature ships dark until then: without `VITE_VAPID_PUBLIC_KEY` the closed-app switch does not render at all.
- The PWA install prompt is now wired (`Header` always accepted the props and was always handed `null`). This matters because **iOS delivers Web Push only to a PWA installed to the home screen** and never fires `beforeinstallprompt`, so without it an iPhone user enables the switch and never receives anything, with nothing explaining why.

### Administrators, announcements and feedback (`admin/`, `announce/`, `feedback/`)

- **One predicate, defined in the database, referenced by everything.** `public.is_admin()` (`supabase/admin.sql`) is `security definer` and answers only about `auth.uid()`, taken from the verified JWT. Every policy and every admin RPC references it, so there is one definition of "administrator" and nowhere for a second to drift. `security definer` is also what stops the recursion of a policy on `user_roles` that calls a function reading `user_roles`.
- **The client is never a security boundary.** `admin/useAdmin.ts` decides whether the Admin tab is *drawn* and nothing else. Forcing it true in devtools yields a console whose every query the database refuses. The role is asked of the server rather than read from `AppState`, because that blob is client-written — a role kept there would be a privilege the client could grant itself from localStorage. For the same reason `user_roles` has **no insert/update/delete policy at all**: under RLS that denies those operations to every client, and the only writers are `grant_admin`/`revoke_admin`, which check `is_admin()` as their first statement. The first administrator is one statement in the SQL editor (`supabase/admin.sql` §7) — a first-run "claim this app" screen is a race anybody who finds the deploy can enter. `revoke_admin` refuses to remove the last one.
- **`announcements`, not `notifications`.** `notify/` already means OS-level notifications here — a Pomodoro bell, a deadline on a lock screen. These are the opposite: one row, written once by a human, read by everybody. Sharing the word would guarantee somebody wires up the wrong one.
- **One global row, per-user acknowledgement.** Publishing fans out to nobody; `announcement_reads` is keyed `(announcement_id, user_id)`, and that composite primary key **is** the deduplication strategy — a double tap, a retry after a dropped connection and a second device all upsert the same row. A `read` boolean on the announcement itself would mean the first student to acknowledge it hid it from everyone.
- Publication is `published_at`, not a boolean: a timestamp answers "is it live" exactly as well and also answers "since when", which is the first thing anyone asks about a notice that went out wrong. Null is a draft, a future value is scheduled, and the SELECT policy — not a client-side filter — is what keeps both invisible. `announce/api.ts` re-filters on top of it anyway, because an **admin's** select policy deliberately returns drafts so the console can list them.
- **It appears on Today, and only on Today.** `useAnnouncements(user, activeTab === 'Today')` is the whole trigger: a forced check on arrival, a throttled one when the tab is foregrounded, and nothing else. No realtime subscription — `user_profiles` has one because a stale AppState on a second device is actively wrong, whereas an announcement arriving four minutes late is not. `supabase/admin.sql` §8 has the one line that adds it if it is ever wanted.
- **Closing is not reading.** Only the explicit button acknowledges; the scrim and Escape set the notice aside, and Today then shows a `NoticeLine` to reopen it. An announcement lost to a stray tap is an announcement that never went out. Multiple unread are walked **sequentially**, oldest first, with "1 of 3" and a "Mark all read" that only appears when there is a backlog — the same stance `UnlockModal` takes on pending rewards.
- `notify/NoticeLine.tsx` is the sleep nudge's pill, **generalized rather than copied**. Its reasoning transfers exactly: Today is for what you need to do today, so a thing that lives somewhere else gets a line and not a card. `analysis/SleepReminder.tsx` keeps only the part that is about sleep — when to show it, and what dismissing it means.
- The modal is built on `UnlockModal`'s shell (same scrim, radius, entrance, footer) because those two are now the only things allowed to stop you on arrival, and two interruptions that look different are two interruptions. `#E10600` is spent on the `important` type alone; a broadcast that arrives in the action colour every time teaches people to stop reading it.
- **Feedback is a form that feels like a chat, and the difference is deliberate.** No typing indicator, no agent avatar, and above all no model answering on behalf of a person. Four categories in one table — abuse included, because they differ in what the form asks and how urgently a human reads them, not in their shape, and a separate `abuse_reports` table would need its own policies and its own chance to get one of them wrong.
- `reported_name` is free text and is deliberately **not** a foreign key to a user: resolving one would mean shipping a user-directory lookup, which is the single thing a report form must not have. Reports are readable by their author and by administrators, and by nobody else — which is what makes the category honest.
- The insert policy pins `auth.uid() = user_id` **and** `status = 'open' and admin_response is null`; without the last two a user could file a ticket that arrived pre-resolved (so nobody read it) or carrying a forged reply from support. Users cannot update their own tickets: an editable message is a message that can be swapped out from under a decision.
- Admin replies are one-directional and not a thread. The submitter reads the reply under their own ticket and cannot answer it; a second message from them is a second ticket. That keeps the feature one table with no unread state, and the inbox shows an email address for anything that needs a real conversation.
- `feedback/api.ts`'s `humanError` is the only thing that reaches a user-facing surface — Postgres' own wording is at best unhelpful and at worst tells somebody exactly which wall they hit. Its `PGRST202`/`PGRST205` cases were checked against a live project, not guessed: PostgREST says "Could not find … in the schema cache", which no `does not exist` test would catch.
- The launcher is **bottom-left** (`.fb-dock` in `index.css`), because `voice/VoiceControl.tsx` owns bottom-right and two floating circles in one corner is how a product ends up with a thumb that can reach neither. Its geometry is CSS rather than Tailwind for the reason the plan grid gives, plus one it does not need: the dock has to clear the fixed rail on desktop and sit in the corner on a phone, which is a media query. `--rail` is set inline from the sidebar's own collapsed state.
- Nothing in either feature touches `AppState`, so nothing here ever fires a Supabase upsert of the whole blob — the same property `share/` has.

### Timer / Lock-In mode

`TimerState` tracks a running study timer per subject with distraction counting (tab switches/blur events) and an `isLockInActive` flag. Starting a session with Lock-In enabled forces the Fullscreen API; exiting fullscreen while active is treated as a "breach" (recorded distraction + forced pause + a "SESSION BREACHED" full-screen interstitial the user must explicitly resume from). Sessions require 15 real minutes (`REQUIRED_FOCUS_MS`) before they can be ended/logged — the end button is disabled and shows a countdown until then. A separate "wipe" affordance (15s press-and-hold) discards the in-progress session instead of logging it. `allowList` in `AppState` is defined in `types.ts` but not currently read/written anywhere in the app — treat it as unused/aspirational state.

### Pomodoro (`today/pomodoro.ts`, `today/usePomodoro.ts`, `today/PomodoroTimer.tsx`)

- **`usePomodoro` is the engine and it is mounted in `App.tsx`, not in the timer component.** A block has to keep running — and keep logging — while the user is on the Streak tab, or on no tab at all. When the loop lived inside `PomodoroTimer` it stopped existing the moment that component unmounted, and the bell never rang. `PomodoroTimer` is a view over the runtime plus the engine's controls; its own 250ms tick only redraws the clock.
- **Time served is never lost.** A block's `DailyLog` is written the instant the block ends — bell, `end()`, `reset()`, or switching to the stopwatch — at neutral quality 4, and rating it afterwards only amends that log (`pendingRating` holds `logId`, never unlogged hours). The old shape parked an unlogged block in `pendingBlock`, so stopping a 60-minute block after 15 minutes threw away the 15 minutes, and a second block finishing before the first was rated overwrote it. `pendingBlock` survives in `types.ts` only to be flushed once from old saved state.
- **Three runtime states, told apart by two fields** (`isIdle`/`isPaused` in `today/pomodoro.ts`): idle is `phaseTotalMs === null`; running has `phaseEndsAt` set; paused keeps `phaseTotalMs` with the time banked in `servedMs`. Everything is derived from the wall clock — `servedMs` is stale by design while running. `phaseTotalMs` is captured at start, so editing the block length mid-phase cannot change what the running block earns.
- Ending a work phase early logs whatever was served (floor `MIN_LOGGABLE_MS`, one minute) and advances to the break, but only fills a dot in the set if at least `COUNTS_TOWARDS_SET` (half) of the block was served — otherwise four ten-second blocks would buy a long break.
- A bell that rang while the tab was hidden is settled at `phaseEndsAt`, so the hours land on the study day they were served, and auto-start is suppressed (chaining off a bell nobody heard fabricates phases). Past `STALE_PHASE_MS` (12h) the phase is dropped instead of logged — the browser was closed, not studied through.
- Settling is idempotent: guarded per `phaseEndsAt` and by a 500ms floor between settles, because a timeout, a 5s safety interval, a visibility handler, a double-tap and a voice command can all reach for the same transition.
- The runtime is device-local — all three sync merge paths in `App.tsx` keep the local `pomodoro` — so `normalizePomodoro` (`state.ts`) only ever sanitizes this device's own localStorage, and `commitPomodoro` bumps `lastUpdated` only when a log is actually written.

## Product philosophy & tone

The product frames studying as high-stakes competition, not a gentle habit tracker — copy is deliberately blunt, uppercase, and pressure-inducing ("THE COMPETITION IS STUDYING. ARE YOU?", "YOUR COMPETITION IS LOGGING HOURS RIGHT NOW.", "Now stop reading and start studying."). Actions are phrased as commitments/consequences (`ENGAGE` / `ABORT`, `WIPE`, `SESSION BREACHED`, `LOCK-OUT: 00:04:12`) rather than neutral CRUD labels. Preserve this voice in any new UI copy — avoid softening it into generic encouragement.

Landing page (`LandingPage.tsx` + `landing/*`) pitches the app as "free JEE study tracker, no fluff" and drives a countdown to JEE Mains 2027, gated behind a one-time `hasVisited` localStorage flag so returning users skip straight to the app.

`OnboardingTour.tsx` runs a short spotlight-based tour (modal → highlight session timer → highlight daily target → highlight Syllabus/Streak nav → closing modal) on first visit to the app proper, tracked separately via the `onboarding_complete` localStorage key. Spotlight targets are located via `data-onboarding-target` attributes on the actual UI elements (see `Sidebar.tsx`), not hardcoded coordinates — new nav items must carry this attribute to stay tour-compatible.

### Design system (`index.css`)

Dark-first "premium" aesthetic: near-black gradient background (`--bg-base #0B0B0D`), a single accent red (`--accent #E10600`) used for progress/action elements, and a light theme variant toggled via `state.theme`. Four fonts are combined intentionally, each scoped to a class:
- `font-display` (Anton, uppercase-only, weight 400) — logo, hero numbers, timers, key stats. Never for body text.
- `font-ui` (Satoshi) — all body/labels/buttons/nav/inputs.
- `font-accent` (Playfair Display) — sparse brand/tagline moments.
- `num-timer` (Averia Serif Libre) — the countdown/session timer specifically, distinct from other stat numbers (`num-stat`, `num-hero` use Anton).
Buttons/cards get a small `active:scale-97` press effect and `.card-interactive` hover-lift globally; the active timer view uses a grain+red-glow "premium" background (`.timer-active-bg`) rather than a flat card.

## Domain model / usage flow

- **Exam preference** (`JEE` vs `NEET`) is chosen at signup and switchable later; it changes which subjects (`getActiveSubjects`/`getCoreSubjects`/`getCoreQSubjects` in `constants.tsx`) and which syllabus chapter set (`SYLLABUS_DATA[11|12]`) are shown, without deleting the other exam's historical data.
- **Tabs** (`Today`, `Plan`, `Syllabus`, `Streak`, `Questions`, `Ranks`, `Review`, `Observatory`, plus `Admin` for staff only) map to the app's core loops:
  - `Plan` — the whole day on one timeline: study alongside class, meals, the gym and sleep, plus a Colours section for recolouring any non-study activity. Drag to move, drag an edge to resize, tap to edit, one-tap quick-add per activity, a Repeat control (just today / every day / every weekday) on each block, and Start now to put the clock on a study block. Dragging a repeating block asks whether you meant that day or the whole series. Plus a repeating-blocks section and a plan-vs-actual adherence readout that grades study only. See Scheduling above.
  - `Today` — start/stop a study session timer (optionally Lock-In-gated), log focus quality (1-5) and manual hours, work a **Todo → Doing → Done card board** (drag between columns, per-card colour, optional deadlines), view today's per-subject hour distribution, and expand a collapsed session history. See Task board above.
  - `Syllabus` — per-chapter status cycling (`not_started → in_progress → completed → revision_pending`) across Class 11/12 chapters for the active exam's subjects.
  - `Streak` — current daily-logging streak (`calculateStreak`, only breaks if neither today nor yesterday has a log), progress to the next reward, a Share Your Win action (see Shareable stats), the reward vault (see Streak rewards below), a 7-day hours bar chart, a monthly heatmap, and (if present) question-practice charts.
  - `Questions` — a separate practice-question tracker (`questions/` dir) with its own weekly/daily goals per subject, "weak subject" flagging, and breakdowns — distinct from the hours/log tracking in `Today`.
  - `Review` — the composite "Lock-In Score" (see `calculateLockInScore` in `utils.ts`), aggregate stats (total hours/sessions/avg quality), account/sync controls (sign in/out, "Reset Device"), exam-preference switch, contact links, and a manual log entry form (for backfilling sessions not tracked live via the timer).
- **Sync/account model**: the app is fully usable offline/local-only (`OFFLINE MODE` badge); signing in via Supabase email/password enables cross-device sync (see Persistence & sync model above). There is no anonymous-to-authenticated data migration beyond the merge-by-id logic already described — signing in on a fresh device pulls cloud state; signing out wipes the local device copy (cloud record is preserved, per the confirm dialog copy).

## Supabase (external, not in this repo)

- Project URL/anon key are hardcoded in `App.tsx` (`SUPABASE_URL`, `SUPABASE_ANON_KEY`) — no `.env`-based Supabase config exists in this repo.
- Single table `user_profiles`: `id` (auth user id, PK), `state` (jsonb serialization of `AppState`), `updated_at`. Realtime is enabled on this table for `UPDATE` events (used for the live cross-device sync channel).
- No migrations/schema files live in this repo — the schema must be inspected/changed directly in the Supabase dashboard.
