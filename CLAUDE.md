# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"LOCK IN JEE'27 Tracker" — a single-page React app for tracking daily study logs, syllabus progress, and question practice for JEE/NEET 2027 aspirants (India). Vite + React 19 + TypeScript, no test framework or linter configured.

## Commands

```bash
npm run dev      # start Vite dev server on port 3000 (host 0.0.0.0)
npm run build    # production build
npm run preview  # preview production build
```

There are no test, lint, or typecheck scripts defined in `package.json`. `tsconfig.json` has `noEmit: true`, so `npx tsc --noEmit` can be used to typecheck manually if needed.

**`tsc` does not check React component props here.** `tsconfig.json` sets neither `esModuleInterop` nor `allowSyntheticDefaultImports`, so the default `import React from 'react'` resolves to `any`, every `React.FC<Props>` is therefore `any`, and JSX prop mismatches — wrong name, wrong type, missing required prop — pass silently. Verify prop wiring by reading it or by running the app; do not trust a clean `tsc` on that specific point. Enabling `esModuleInterop` would restore the checking but will surface pre-existing errors across the codebase.

Environment variable `GEMINI_API_KEY` is read via `vite.config.ts` and exposed as `process.env.API_KEY` / `process.env.GEMINI_API_KEY` (not currently referenced elsewhere in the code).

## Architecture

- **Monolithic `App.tsx`** (~1800 lines) contains the root `App` component plus most tab components defined inline as local consts: `AuthModal`, `Navbar`, `TaskSection`, `SyllabusTab`, `MonthlyHeatmap`, `StreakTab`, `ReviewTab`, `TodayTab`. When making changes, search within this file rather than assuming separate component files exist.
- **Separate top-level components**: `Sidebar.tsx`, `LandingPage.tsx`, `OnboardingTour.tsx`, `site/` (static syllabus guide pages — see Guide pages below), and the `landing/` (the pre-rendered landing page — see Landing page below), `mocks/` (Mocks tab + error notebook) and `notes/` (the Notes tab — see Alpha Notes below) directories. `questions/` now holds only `utils.ts`, which the Streak tab's question charts still read — the Questions tab itself was removed.
- **`review/`** holds chart components (`QuestionsBarChart`, `QuestionsHeatmap`) used by `ReviewTab`.
- **State shape** is centralized in `types.ts` (`AppState`), covering logs, syllabus progress, tasks, timer, question tracking, and theme. `constants.tsx` holds static config: syllabus chapter lists per class/subject, status colors/labels, exam-preference helpers (`getActiveSubjects`, `getCoreSubjects`, `getCoreQSubjects` switch behavior between JEE and NEET), and exam countdown target dates.
- **`utils.ts`** has pure functions operating on `AppState`/`DailyLog[]`: IST date handling (`getISTDateString` — all dates are computed in Asia/Kolkata timezone, not local time), streak calculation, 7-day stats, subject distribution, and the "Lock-In Score" composite metric (consistency 30% + volume 30% + syllabus progress 10% + quality 30%, minus a distraction penalty).

### Persistence & sync model (in `App.tsx`)

- Local-first: full `AppState` is persisted to `localStorage` under key `locked_in_state_v2` on every state change.
- Optional cloud sync via Supabase (`@supabase/supabase-js`), table `user_profiles` (columns: `id`, `state` jsonb, `updated_at`). The Supabase URL/anon key are hardcoded in `App.tsx`.
- Conflict resolution uses a `lastUpdated` timestamp on `AppState`: on initial sync, whichever of local/remote has the newer `lastUpdated` wins wholesale, except when local is newer, in which case `logs`/`tasks` are merged by `id` to avoid resurrecting deletions while keeping unique entries from both sides. UI-only fields (`lastUsedTab`, `theme`) always stay local.
- A Supabase Realtime channel (`profile_changes_${user.id}`) listens for `UPDATE` on `user_profiles` and applies remote state locally if its `lastUpdated` is newer, guarded by a `preventSyncOnUpdate` ref to avoid sync feedback loops.
- `triggerSync` upserts state to Supabase, debounced via `isSyncingRef`/`pendingSyncRef` so overlapping writes queue rather than race. The push effect is keyed on `[state, user?.id]`, **never the `user` object**: supabase-js re-emits `SIGNED_IN`/`TOKEN_REFRESHED` with a freshly parsed user on every return to the foreground, so keying on the object pushed on every resume, and a phone resumed from memory stamped its stale copy as the account's newest state.
- `timer` and `pomodoro` are device-local in every merge path, and **`timerMode` is held with them while one is armed** (`heldMode` in `today/pomodoro.ts`); otherwise it syncs as a preference. Readers use `effectiveMode(state)`, not `state.timerMode`. A phone's synced Stopwatch landing on a laptop mid-block used to hide the block's controls and leave the mode switch locked by the block it hid.
- Auth is **Google only** (`AuthModal`, `supabase.auth.signInWithOAuth`); email/password sign-up and sign-in were removed. An old email/password account is reached by signing in with Google on the same address (Supabase links the identity). Signed out is a guest: everything stays local; signing out clears all `sb-*` and the `locked_in_state_v2` localStorage keys and resets to `DEFAULT_STATE`.

### Streak rewards (`rewards/`)

- Milestones live in `rewards/catalog.ts` (`REWARDS`) — day 30 wallpaper pack, day 100 in-app book, day 365 physical hamper. Adding a tier is one entry there, provided its `kind` already has a way to be opened. Nothing else hardcodes a milestone.
- `rewards/engine.ts` is pure: `evaluate` re-derives unlocks from logs on every `state.logs` change (returns the *same* object when nothing changed, so the effect settles in one pass). Because it runs on mount, users with pre-existing streaks get their tiers backfilled.
- **Unlocks come from the longest run in the history, not the live streak.** `evaluate` uses `longestStreak`/`longestVerifiedStreak` (`utils.ts`) over all logs, so a month that ended in March still pays out, and a backfilled month counts. The earlier rule read `calculateStreak`, which only sees the run reaching today — a completed 30-day run that broke before the vault was next opened was never rewarded at all.
- **Progress is measured by the live streak.** `rewardProgress(rewards, streak, verifiedStreak)` — the days-to-go line has to answer "what does one more day buy me". Driving it off the high-water mark froze the whole vault for anyone rebuilding after a break (day 8 of a new run, best of 12 → "18 days to go", unchanged for four days running, directly under a card reading "Current streak: 8"). The stored best is shown beside the bar as `best N` when it beats the run in progress, and nothing else.
- **Unlocks are permanent and monotone.** Breaking a streak never revokes one. `RewardsState` stores `bestStreak`/`bestVerifiedStreak` high-water marks so deleting old logs cannot take a reward back either. That one-way property is why `mergeRewards` unions rewards on sync instead of letting last-write-wins drop a tier — it is applied in all three merge paths in `App.tsx` (cloud-newer, local-newer, realtime).
- Rewards with real cost behind them (`requiresVerified: true` — book, hamper) count only the **verified streak**: consecutive days with a `timer`/`pomodoro` log, never held by firewood, via `calculateVerifiedStreak` in `utils.ts`. Manual backfills keep the visible streak alive but cannot mint a year of study in a for-loop. Same stance the leaderboard takes on `LogSource`.
- UI: `RewardsVault` (in `StreakTab`) shows locked tiers too — a prize you cannot see is not a reason to log tomorrow. `UnlockModal` fires once per reward, oldest un-shown first, gated on `acknowledged`.
- Wallpapers (`rewards/wallpapers.ts`) ship no image assets — every design is layered CSS, plus SVG data URIs generated at module init by `starfield()` (a seeded PRNG placing individual stars; tiled `radial-gradient` dots were tried first and always read as graph paper). `rewards/WallpaperLayer.tsx` paints both the fixed full-page layer in `App.tsx` and the picker swatches, so a preview is exactly what gets applied.
- The Aurora wallpaper is animated, which a CSS `background` cannot be — it renders real elements: `AURORA_CURTAINS` (masked ribbons of hairline "rays" over a luminous sheet) and `AURORA_GLOWS` (unmasked, heavily blurred ambient spill so the light falls off across the page instead of stopping at the mask). Motion lives in `index.css` (`aurora-drift`/`aurora-glow`/`aurora-shimmer`/`aurora-breathe`) and is disabled under `prefers-reduced-motion`. Per-element `animationDuration` must list one value **per keyframe animation** — a single value silently applies to all of them and locks the cycles together.
- Two things constrain every wallpaper: they sit behind the header, so peak brightness has to leave the countdown text readable; and the same CSS paints a 64px swatch, so no viewport units.
- **The day-100 book is the author's LOCK IN.** `content/book.ts` holds the shape (`BookBlock` kinds: p, h, h3, quote, line, action, list, fragment; chapters may open a `part`) and the cover facts the vault reads (`BOOK`, with `chapterCount` so the vault never loads the text). The text is `content/bookText.ts`, reachable only through the lazy `BookReader` chunk (~34 kB gz), so the main bundle carries none of it. **Every block and list item has a permanent id** (`ch1.07`, `ch1.12.3`) that highlights, notes and bookmarks anchor to: edit text in place, give a new block a new id (`ch1.07a`), never renumber. Inline marks are `*italic*` and `**bold**` only. It was rebuilt by hand from a Canva PDF whose text layer was damaged (glued words, doubled fi/fl, broken lines, missing dashes) and checked word for word against it; `content/BOOK_NOTES.md` lists what was repaired and the author's typos left for them to decide. See The reader below.
- The hamper claim is deliberately a `mailto:`, not a form. The app never collects a postal address — most users are minors, and shipping details in a synced jsonb blob is a liability, not a feature.

### The reader (`reader/`)

- **The day-100 book's reader**, lazy with the text (`rewards/BookReader.tsx` re-exports `reader/Reader.tsx`, so App's one lazy import brings both; ~46 kB gz, nothing in the main bundle). One chapter at a time, scrolled, set in **Literata** (Google Play Books' screen face, optical sizes; injected when the reader opens, Georgia until it lands) or Satoshi. Kicker + title opener, a drop cap on the first paragraph, a part page for "Level 2.", Action Steps as cards with a **Mark done** tick (sound `task-done`), an end-of-chapter card with what's next, and an end-of-book page with the student's own stats. The chrome hides on scroll down and returns on scroll up, at the end, or on a tap of the page; a red hairline along the bottom is always the book's progress.
- **`reader/model.ts` is pure and tested** (`npm run test:reader`): units, inline marks, highlight segments, search, progress, and the `reading` AppState slice. **A point in the book is `{ u, o }`**: a unit id (a block or list item's permanent id; part intros are `<chapter>.part<n>`) and an offset into its *plain* text (marks removed). Every unit renders as one `[data-u]` element whose text nodes are exactly that plain text, so a DOM point's offset is `Range(unit → point).toString().length` (`reader/anchors.ts`). **Nothing that is not book text may put a text node inside a unit**: the note pin is an SVG button with an aria-label and no `<title>`, the drop cap is CSS. A highlight also keeps its `quote`; `resolveHighlight` re-finds it by text if the manuscript moves under it.
- Selections are trimmed of edge whitespace and **snapped out to whole words** (`snapToWords`) before anything is saved. The toolbar sits **below** a selection on touch screens (iOS draws its own Copy callout above) and above it with a mouse; its pointerdown is prevented so pressing it never clears the selection. Overlapping highlights paint the newest on top. Tapping a highlight opens colour / note / copy / remove; remove is a tombstone with an Undo toast.
- **What syncs and what doesn't.** `AppState.reading` (`ReadingState`) holds highlights, bookmarks, the position, each chapter's furthest point and Action Step ticks; App normalizes it on read and on load (where the old `rewards.bookChapter` index migrates to a position via `BOOK.chapterIds`, so the text is not needed in the main bundle), and `mergeReading` runs in the **local-newer path only**, like `mergeMocks`. **Deletions are dated tombstones** (`deletedAt`, pruned after 60 days) and unticks are negative timestamps, so a union can never resurrect what another device removed; everything that draws filters with `live()`. Reading settings (page colour Paper/Sepia/Dusk/Night or auto from the app theme, face, 8 sizes, spacing, line length, justify) are **device-local** (`reader_settings_v1`), like sound. The last highlight colour is too.
- **The position is measured on every scroll and written rarely.** The unit on the reading line (30% down) and the fraction through it go to a ref and, throttled, to this device's `reader_pos_v1`; AppState gets it only on chapter change, close, tab hide/pagehide and every 30s, and only when it moved. Opening takes the newer of the device's and the account's position. After Literata loads, an untouched page is put back on the same words; a settings change keeps the same words on the reading line (or the top, if you were at the top). A note is written once, when its editor closes (any way of closing saves).
- Panels: the **drawer** (Contents with progress rings and the part divider; Notebook with the folded Action Steps checklist, colour/notes filters, entries in book order and **Copy all** as Markdown; Marks; Search, which folds ’ → ' and … → ... so "dont"/"don't" find "don’t"), the **settings** popover (a bottom sheet on a phone), the **note sheet** (full screen on a phone). Keys: ←/→ chapters, `/` or ⌘F search, B bookmark, C contents, N notebook, +/− size, ⌘↵ saves a note, Esc steps back one layer at a time.
- Styling is hand-written `reader/reader.css` scoped under `.rd`, not Tailwind: every page colour defines its own ink, rules and highlight tints. Ragged right with no hyphens (`text-wrap: pretty`); justify turns hyphenation on, limited to long words. `#E10600` is spent on the progress line, the Keep reading button, Action Step labels and the bookmark ribbon only.
- **The reader's components take explicit prop types** (`({ … }: Props)`), not `React.FC<Props>`: as noted at the top, `React.FC` is `any` here, which silently untyped every prop and every generic inference downstream (`live()` fell back to its constraint). New reader components should keep that pattern; it is also why `tsc` checks their props.
- **`?book=debug` (DEV) is the design board**: a live phone and laptop frame, then every state at real device sizes (reading, chrome away, opener, Level 2, selecting, highlight menu, note, settings, contents, notebook, bookmarks, search, chapter end, book end, empty notebook), all four page colours, Satoshi and the largest size, on three histories (first open, mid-book, finished) built from the real text. Frames are iframes of `&stage=1&fx=…&page=…&panel=…&ch=…`, and settings are pinned per frame so nothing leaks through shared localStorage.

### Festive themes (`festive/`, `supabase/festive.sql`, `admin/ThemeAdmin.tsx`)

- **One global switch, set by an administrator in Console → Theme**: `none | dussehra | diwali | christmas`. Dussehra is the toran and a row of diyas; Diwali is a string of paper lanterns, the akash kandil, diyas, rising sparks and a tappable firecracker box. `festive.sql` replaces the CHECK by name, so re-running it upgrades a table made when Dussehra and Diwali were one theme. It lives in the single-row `app_settings` table, readable by everyone including `anon` (guests see the theme too), with no write policy; the only writer is `admin_set_festive_theme`, which checks `is_admin()` first. Never in `AppState` — a per-student, client-written blob cannot hold a global setting.
- `useFestiveTheme` (App root, above the early return) reads it on load, listens for the Realtime UPDATE so a flip reaches open tabs within a second, re-reads on return to the foreground (2-min throttle), and caches the last answer in localStorage (`alpha_festive_v1`) so a reload paints it on the first frame. Before `festive.sql` is run everything fails quiet and the app looks as it always has. DEV: `?festive=dussehra|diwali|christmas|none` forces one without a database.
- `FestiveLayer` is lazy (~4 kB gz with its CSS) and sits at `z-1`, over the page background and under `<main>` (z-20): cards cover it, it shows in gutters and along edges, takes no pointer events, and stops moving under reduced motion. All artwork is SVG data URIs in `festive/art.ts` — no image files. Repeating pieces (the marigold toran, the string of lights) are one tile on `repeat-x`. Snow is a canvas that runs only while the tab is visible.
- **The firecracker box is the only thing in the layer that takes a pointer.** A tap calls `launch` in `festive/fireworks.ts`: one full-window canvas (z 60: over the page and rail, under sheets) made on the first launch and removed when the sky is empty. Trails are `destination-out` fades, the only way to streak on a transparent canvas over the app. Shells are peony / ring / gold willow in one or two random colours. Sound is synthesised from noise in its own AudioContext and obeys the app's mute and volume. The box renders **outside** `.fx-root`: the root sits under `<main>`, and on a narrow screen the box must sit over the page, left of the settings gear (`dock`); with a wide right gutter it stands above the gear (`gutter`).
- **On a phone the strings hang under the glass capsule, not behind it** (`--fx-top` = safe + 62px), a size smaller, and `.shell-offset.festive-pad` (in `index.css`, so it lands with the first paint rather than with the lazy chunk) pushes the page down 34px so the title clears them.
- **A student can turn the live theme off** in quick settings (a "Festive theme" switch under Dark mode, drawn only while a theme is live). `useFestiveOptOut` stores **which** theme was turned off (`alpha_festive_off_v1`), not a blanket "off": hiding Diwali must not silently swallow Christmas, so a new theme brings the switch back on. Device-local like sound, never AppState. App passes the effective theme (`festive`) to the layer and Today's greeting, and the live one (`festiveLive`) to the settings row.
- **`?festive=debug` (DEV only) is the design board**: each theme in phone/laptop/wide frames, dark, light or both, rail open or collapsed, plus 2× close-ups and every console swatch. The frames are iframes of a stage (`&stage=1&theme=…&mode=…&rail=…`) at real device widths, because the layer places its pieces from its own window's width; a scaled div would lie about the gutter and the phone breakpoint. Salvo posts a message to every frame to fire five rockets from its cracker box.
- The hanging ornament (left) and greeting plaque (right) are drawn only when the gutter beside `<main>` can hold them (`useGutter`); a plaque reaching under the page header collided with the exam countdown. On every screen size the greeting also appears in Today's date line (`FESTIVE_GREETING`), in the theme's own ink — never `#E10600`.

### Scheduling (`schedule/`)

- The **Plan** tab, and it schedules the *whole* day, not only study. `schedule/schedule.ts` is pure and React-free (same contract as `today/pomodoro.ts`); `PlanTab.tsx` is a zero-logic container over `DateStrip`, `DayTimeline`, `AdherenceSection` and `TemplateSection`, taking a narrow slice plus narrow callbacks like `mocks/MocksTab.tsx` — never `AppState` or `setState`.
- **`BlockKind` is the primary axis, not `Subject`.** `schedule/colors.ts` holds `ACTIVITIES`, the single registry of what a block can be (study/revision/test, then class/sleep/meal/gym/break/travel/other) along with its label and a sensible default time and length for one-tap adding. `ScheduleBlock.subject` is therefore **optional** — sleep has no subject, and giving it a phantom `General` would drag it into the adherence maths. `countsAsStudy(kind)` is the one predicate that decides what is measured; `blockStyle`/`blockTitle` decide how a block reads. Study blocks are coloured by subject, life blocks by kind and deliberately low-chroma, so the work stays the thing your eye lands on.
- Times are shown as **12-hour with AM/PM** (`formatClock` "6:30 AM", `formatHour` "6 AM" for the axis gutter, `formatRange` writing the meridiem once when both ends share it: "6:00 – 7:30 AM" but "11:00 AM – 1:00 PM"). `DayMinute` stays 24-hour arithmetic from 04:00; the meridiem is presentation only.
- The editor asks **what it is first**, and only then shows the fields that kind actually has — subject and chapter for study, a free-text name for everything else. Switching families clears the detail that no longer applies, so a block cannot keep a subject it stopped having. Two rules keep the sheet from being a wall of chips: **colour carries the selection where colour means something** (a kind or subject chip wears its own colour when chosen, so the row doubles as the legend and the header previews the block you are about to make; durations and repeat keep the accent), and **time is typed, not stepped** — start and end are real `<input type="time">`, so 6:45 is one entry rather than five taps, the OS supplies the phone keyboard, and the duration row is a shortcut rather than the only route. `toClockValue`/`fromClockValue` bridge the 04:00 axis: typing an end of 1:30 on an 11 PM block gives 2h 30m, because 1:30 is simply later on that axis. The footer is `sticky bottom-0` — the button that commits the block should never be somewhere you scroll to find.
- The clash warning **names what you collide with** ("Overlaps Coaching"), not how many — a count made you close the sheet to find out which.
- A block cannot straddle the 04:00 rollover, so sleep entered as 11 PM–7 AM clamps to **11 PM – 4 AM** and the editor says so; the remainder is a second block on the next day. Splitting it automatically would give the user two halves that drag and delete independently, which is worse than the honest clamp.
- **`DayMinute` is minutes since 04:00 IST, not since midnight.** Minute 0 is 04:00, 1200 is midnight, 1439 is 03:59 the next morning. Storing wall-clock minutes instead would make a 23:00–01:00 block wrap, and every one of overlap detection, sorting, layout, drag-clamping and hit-testing would need a special case. `start + durationMins <= 1440` is a hard clamp everywhere (`clampBlock`) — a block may not straddle the rollover, or its hours would land on two study days and be unfalsifiable against `logs`. The grid draws a labelled `MIDNIGHT` divider at 1200 so the wrap is legible.
- **Recurrence is rules plus per-date overrides, never materialized rows.** `TemplateRule` has `days`/`from`/`until`; `materializeDay(schedule, date)` derives instances on read and gives each the synthetic id `` `${ruleId}@${date}` `` — the same key a `BlockOverride` uses, so an instance has a stable identity without anything being written for days you never touched. Writing seven rows a week would grow the synced jsonb blob without bound and would need a nightly job that has nowhere to run.
- **Repeat is a first-class control in the editor, not a hidden action.** `RepeatMode` is `none | daily | weekly | custom`; `daily` is simply a `TemplateRule` whose `days` is all seven, so nothing in the model special-cases it. `custom` is the days the three buttons cannot name (Mon–Fri, Tue/Thu) — `repeatOf` used to read any sub-seven rule as `weekly`, so opening a Mon–Fri coaching block on a Tuesday and pressing Save silently deleted the other four days; `daysForRepeat` now takes the rule's current `days` and hands them straight back for that mode. The choice is applied by `saveDraft` alongside every other field, which handles all six transitions (new/existing × one-off/repeating). It replaced a buried "Repeat weekly" link that always wrote `days: [today's weekday]` — users read "repeat", looked at tomorrow, saw nothing, and reasonably concluded it was broken. Turning a repeat back off deletes the rule **and writes a one-off for the day you are on**: the user asked for one block, not for none.
- **Deleting a repeating block asks which one you mean.** "Delete from today" writes a skip override; "Delete from every day" deletes the rule. A single "Delete" removes the wrong one for half the people.
- **Editing a rule closes it and opens a new one** (`updateRule` in `App.tsx`: old rule's `until` = yesterday, a new rule `from` today), and `deleteRule` sets `until` rather than removing the row. Editing in place would move the slot on days already spent, so last Monday's adherence would silently be re-measured against a plan that did not exist when it was lived. A rule starting today or later has no such history and really is edited/removed outright. **The reopened rule takes its still-future overrides with it** — they are keyed by rule id, so re-opening under a new id used to orphan every one: a day skipped next week came back, a day moved next week jumped. Overrides on days already lived stay with the closed rule, which is the whole point of closing it.
- **Dragging a repeating block asks which one you mean too** (`ScopePrompt`, same stance as delete). A drag of a rule instance is ambiguous between "this Tuesday" and "every Tuesday"; `DayTimeline` still commits once on release, but `PlanTab` holds the geometry in `pendingMove` and writes nothing until the user answers. It is one tick box — "Move every day?", **ticked by default**, because you dragged the block a repeat put there and so most of the time you meant the repeat — over a single Move it button. Ticked calls `updateRule` with `clearOverrideOn: date`, so the day you dragged is not left as the one exception to the change you just applied to every day; unticked writes an override for that date (`updateBlock` routes on whether the id contains `@`). Answering silently — always "this day only" — is what made a plan look right today and land in overlapping pieces tomorrow: a student who built a repeating skeleton and then tidied it by dragging saw every block snap back to its pre-drag time the next morning. While the prompt is up the block is drawn where it was dropped; cancelling reverts it, since nothing was written. `normalizeSchedule` (`state.ts`) drops overrides whose rule is gone, which is what keeps that array bounded.
- A rule created from the grid starts on the **day being planned**, not unconditionally today (`addRule` takes an optional `from`, clamped to no earlier than today) — turning tomorrow's block into a repeat must not also drop it onto the day you are standing in.
- **A gesture never touches `AppState`.** Every state change writes localStorage and fires `triggerSync`, so committing per frame would mean ~60 Supabase upserts per drag. `DayTimeline` keeps live geometry in a `preview` state plus a `dragRef`, and calls the mutator exactly once on release. Pointer Events, not HTML5 drag-and-drop (no touch support, no resize); `pointermove`/`up` are bound to **window**, because `setPointerCapture` routes captured events back to the element that claimed them and a handler anywhere else would never fire. A `ref`-only gesture cannot wake an effect, hence the `gesture` state whose only job is attaching those listeners. `pointerup` after a real drag sets `suppressClickRef` so the trailing click does not open the editor on the block just moved.
- All block geometry is **inline `style`**, never Tailwind. Tailwind here is the CDN script with no config, so `h-[${n}px]` in a template literal compiles to nothing. `touchAction: 'none'` on cards and handles is what makes touch dragging work at all; the 56px hour gutter stays scrollable so the grid can still be panned on a phone.
- Overlaps are allowed, never blocked — `layoutDay` splits clashing blocks into side-by-side lanes and the editor warns without refusing. A student double-booked at 19:00 is information; refusing the drop reads as the app being broken.
- **Past days are read-only.** Editing yesterday's plan after the fact would falsify its adherence.
- **Only study is graded.** `computeAdherence` filters to `countsAsStudy(kind) && !!subject` — you do not get marked down on dinner, and a block with no subject could never be matched to a log, which carries one.
- **Adherence is two-tier, and the UI says which.** `DailyLog` has a date, a subject and hours but **no start time**, so per-block truth exists only when the app was watching: `startBlock` stamps `TimerState.blockId`/`chapter`, `handleStopTimer` passes them to `logStudy`, and they land on the log (this is also why `logStudy` gained trailing optional `chapter`/`blockId` params, and why `engageRecommendation` now carries `rec.chapter` — `hoursOnChapter` in `recommend.ts` had been reading a field nothing ever wrote). Everything else is allocated by subject, **earliest block first** — the charitable reading that still leaves a late block correctly marked skipped — and the leftover is `offPlanMins`. Blocks of kind `break`/`fixed` are commitments and never count as planned study.
- **Subject colours are data; everything else is the user's.** `schedule/colors.ts` is the app's only subject colour map, and `SUBJECT_COLORS` is fixed — Physics is that blue on the grid, in the charts and on every device, and a subject you can recolour is a subject you can no longer read at a glance. Every non-study kind (`RECOLOURABLE`) is the user's to pick, from twelve presets or a native `<input type="color">`, in `PaletteSection` on the Plan tab; the choice lives in `state.schedule.colors` keyed by `BlockKind`. Defaults (`ACTIVITY_BASE`) are saturated on purpose — the old near-grey life palette kept the work in front but made the tab look like a spreadsheet, and study blocks already win by carrying a subject colour and a chapter name.
- **Every block colour is applied inline, never as a Tailwind class.** `BlockStyle` now holds CSS colour strings rather than class names, because a user-picked hex cannot become a class here (CDN Tailwind, no JIT over template literals — `bg-[${hex}]` compiles to nothing). Activity styles are computed from one hex by `derive`: translucent `rgba` fill and border so a block reads as tinted glass on either ground, and text mixed toward white on dark / black on light so a saturated pick stays legible. Subject values stay spelled out literally so they render byte-identical to before.
- A stored colour ends up in an inline `style`, so `normalizeSchedule` validates it against `HEX_RE` (`#rrggbb`, nothing else) and drops keys for study kinds outright. `mergeSchedule` merges the colour maps key-by-key with local winning — they are settings, not rows, so there is nothing to lose by keeping the other device's picks.
- The accent `#E10600` is deliberately absent from both palettes and from the preset list — that belongs to the now-line and to actions.
- **Styling follows the house card style (now carried by `mocks/ui.tsx`), not `today/`**: card `p-8 md:p-10 rounded-xl border` with `bg-[#111114] border-white/[0.06]` dark / `bg-white border-zinc-100 shadow-sm` light; section headings are small eyebrows (`text-[10px] font-bold uppercase tracking-[0.06em]` in `text-zinc-500`/`text-zinc-400`), not display type; muted text uses the zinc scale rather than white/black alphas.
- `mergeSchedule` runs in the **local-newer sync path only**, exactly like the by-id merges of `logs`/`tasks`. A union in the realtime or cloud-newer paths would look kinder and be wrong: a block deleted on the phone has to reach the laptop, and a device that unions can never be told something is gone.

### Mock tests and the error notebook (`mocks/`)

- The **Mocks** tab took the Questions tab's slot in the rail. A saved `lastUsedTab: 'Questions'` is mapped to `'Mocks'` on load in `App.tsx`. Everything lives in `AppState.mocks` (`MocksState`: `tests`, `errors`, `topics`); `normalizeMocks`/`mergeMocks` are in `mocks/model.ts`. `mergeMocks` runs in the **local-newer sync path only**, like the by-id merges of logs and tasks: union by id, later `updatedAt` wins, so a result logged on one device is never overwritten by the other's stale plan. App also normalizes on read (`useMemo`), because the realtime path can spread a blob with no `mocks` in it.
- `MocksTab.tsx` is a zero-logic container like `schedule/PlanTab.tsx`. App passes only upsert/delete callbacks. **`mocks/insights.ts` is the only file that does arithmetic about performance**, the same stance as `share/stats.ts`; components ask it questions.
- **Two classification axes, and both apply everywhere.** `MockExam` (`mains`/`advanced`/`neet`/`other`, offered per `examsFor(pref)`) and `MockScope` (`full`/`part`/`chapter`). The filter row applies to *every* analytical panel at once: tiles, trend, subjects, mistakes, weak spots and insights. **The trend draws one line per exam *and* scope.** Colour is the exam. The marker shape is the scope (● full, ○ part, ◆ chapter). Full papers get the strong line and part tests a lighter one. Chapter tests get dots only, because two chapter tests on unrelated chapters are not a trend. Joining a 72% chapter test to full-paper scores drew a peak that never happened. For the same reason, the default scope filter is **full** whenever full mocks exist (`Prefs.scope` absent = smart default). The filter is per-device in localStorage, never `AppState`.
- **"Other" papers are named by the student.** `MockTest.paperName`/`maxMarks` exist for `exam: 'other'` only. A named paper (e.g. "BITSAT", 390 marks) is its own classification: `paperKey(test)` (`'mains'`, or `'other:bitsat'`) is what filter chips, trend lines, "vs last" deltas, momentum insights and auto-numbered names group by, and `paperLabel`/`paperShort` are what badges print. Use those helpers, never `test.exam`, whenever two mocks are being compared. `maxMarks` is only the default for a blank result. `blankScores` splits it across subjects in whole marks, and each subject's max stays editable on the result sheet. Named papers share the "Other" hue; the legend and the end labels carry the names. The ExamFilter preference stores a `paperKey`, so an old `'mains'` value still works.
- Exam colours were run through the dataviz palette validator. Main/Advanced/Other pass in both modes. **NEET shares Main's slot**, because NEET against a fourth hue failed the dark-mode CVD floor and no student plots both. Mistake-type colours are slots 4–7 and pass as an adjacent stack. `#E10600` is in neither palette.
- A mock is planned or taken by whether it has a `result`. It is one row for both, so the chapters picked while planning are the chapters reviewed afterwards. A full-syllabus mock stores no chapter list; after it, the student adds the chapters worth remembering. `MockResult.verdicts` are keyed by `chapterKey`/`topicKey` (`11|Physics|Chapter|Topic`); absence means "no opinion". Weak spots weight recent mocks more, boost heavyweight chapters via `getWeight`, and drop a leak whose last verdict was strong (it moves to "Fixed").
- **Topics are names, not ids.** Authored topics (`content/topics.ts`) and the student's own (`mocks.topics`, keyed per chapter) share one list, so a typed "Moment of inertia" is offered back next time.
- The result sheet works out marks from right/wrong counts when the paper has a fixed scheme (`EXAMS[exam].scheme`, e.g. Main 4/−1) but never overrides marks the student typed — bonus questions exist. "Questions you lost" is counted in questions; "≈ marks" is questions × `perQuestion`.
- The upcoming mock's readiness reads `state.progress`. This is the only place the tab reads the Syllabus tab: chapters in the paper that aren't started get named on the hero card and in the insights.
- **Error notebook.** `ErrorEntry` is text only, with exactly four options. Most JEE questions have a figure, but an image inside the synced jsonb blob would be re-uploaded on every change. The form follows the student's own order: question → options → correct option → why (a required `ErrorReason`, plus their own words) → chapter → optional topic. "Save & add another" keeps the chapter. Errors can be logged from inside a mock's result and remember `mockId`. Deleting the mock keeps the error and drops the pointer.
- **Error tests** (`ErrorQuiz.tsx`): **options are shuffled every run**, because remembering "it was C" is recall of a letter, not of physics. Feedback is immediate and shows the student's own note from when they logged it. **Two right in a row clears an error** (`CLEAR_STREAK`). `practiceOrder` asks recently-wrong first, then never-attempted, then the rest, with cleared ones last. The whole run is **one `AppState` write** (`applyAttempts`) when it ends or is abandoned, never one per answer. "Retry the ones you missed" reads fresh copies from props, so the streak shown is the post-run one.
- **Every sheet and the error test render through `Overlay` (a portal to `document.body`).** `<main>` is `relative z-20`, so a fixed element inside it, whatever its z-index, paints under the `z-50` rail and the phone's top bar. The full-screen test lost its close button to the sidebar before this.
- Bounds (`normalizeMocks`): 400 mocks, 800 errors, 1,500-char questions, 300-char options, 40 topics per chapter. These ride the synced blob.

### Private CBT and question bank (`cbt/`, `supabase/cbt.sql`, `scripts/qbank/`)

- **Private, gated in the database.** A third Mocks segment, **Question bank**, drawn only for accounts in `public.user_features` with `feature = 'cbt'`. The grant is a hand-run insert (`cbt.sql` §7). There is no in-app way to give it, on purpose. `has_feature()` mirrors `is_admin()`: definer, `auth.uid()` only, revoked from `public, anon`. Every table, the private `qbank` storage bucket (paths `<uid>/<source>/<file>`) and every policy re-check it per statement, so deleting the grant locks the bank at once and re-inserting it restores it untouched. `cbt/useFeature.ts` only decides whether the segment is drawn. Tested in PGlite (37 scenarios: other users, a second feature holder, spoofed `user_id`, filing under someone else's source, revoke/regrant, storage folders).
- **Nothing in `AppState` except the result.** The bank (`qbank_sources`, `qbank_questions`) and sittings (`cbt_papers`) are server tables. A finished paper becomes one `MockTest` (`series: 'Alpha CBT'`, exact per-subject counts, `cbtPaperId`) plus `ErrorEntry`s, written in **one** `withMocks` call (`saveCbtResult` in `App.tsx`). Mocks and the notebook receive ordinary rows. A question already open in the notebook is updated (same id, streak to 0), never duplicated.
- **Reading PDFs happens on the laptop**, not in the app: `scripts/qbank/extract.py` (DeepSeek `deepseek-flash` vision, OpenAI-compatible, key in env) writes an `alpha-qbank/1` JSON with figures as data URIs. `cbt/bundle.ts` validates it field by field and decides status itself: no answer → `ungraded`; answer + a chapter that exists in `getChaptersFor` + confidence ≥ 0.85 → `ready`; else `needs_review`. A CHECK makes `ready` impossible without an answer and a chapter. `text_hash` (normalised text, unique per user) is the dedupe. A failed import deletes its own source, because the PDF hash is unique and a half-import would block a retry. `scripts/qbank/chapters.json` is generated from `constants.tsx` (`npm run qbank:chapters`).
- **Generator (`cbt/generate.ts`) is pure and seeded** (mulberry32). Per section: slots split across chapters by `getWeight` × availability (largest remainder), capped per chapter (3 MCQ / 1 numerical), weak chapters from `topLeaks` ×1.4. Inside a chapter, a weighted draw on freshness (seen < 21 days excluded; an open notebook error returns after 7), difficulty mix and year spread. When the bank is thin it relaxes recency, then the cap, and **writes every relaxation into `blueprint.notes`**, shown before the clock starts. Chosen-chapter papers are uncapped and equal-weighted.
- **The exam (`CbtExam.tsx`) follows NTA's rule: an answer counts only once saved** (Save & Next / Mark for Review & Next; `amr` counts, `mr` doesn't). The pick is reset **in the same update as the move** (`moveTo`), never in an effect. An effect let a fast double-press carry one question's pick onto the next and save it there. Time per question is read outside state updaters (StrictMode runs them twice). The clock is wall time from `startedAt`: leaving doesn't pause it, and a paper reopened past its end submits at once. Responses go to localStorage on every change, to the DB each minute, on subject change and when the tab hides, and in full at submit.
- **Auto verdicts judge only questions the student opened.** Never-visited questions (clock ran out, subject left for last) say nothing about a chapter, and called "weak" they flooded the weak-spot board after every rushed paper. Two opened questions are needed for a verdict. All of them are editable before saving.
- **KaTeX is lazy.** `cbt/Tex.tsx` (KaTeX + CSS, ~264 kB) is reached only through `React.lazy`: from `BankView`/`PaperViewer` in `MocksTab`, and from `mocks/QText.tsx` for notebook entries with a `qbankId`. Hand-typed errors render as plain text and never load it. Markup is `$…$`/`$$…$$`/`\(…\)`/`\[…\]` plus `[[fig:N]]` → `figures[N]` (signed URLs, cached in `cbt/figures.ts`).
- `ErrorEntry` gained `qbankId`/`figures`/`numeric`. A numerical entry has four empty `options` and `correct: 0`. `normalizeError` widens its text caps for bank entries (cutting LaTeX mid-expression breaks the render), and `ErrorForm` shows bank questions read-only.
- Dev harness: **`?cbt=debug`** runs the exam, review and error test on a fixture bank with no database (`cbt/DebugCbt.tsx`, DEV-only, tree-shaken).

### Alpha Decks — spaced-repetition flashcards (`decks/`, `supabase/decks.sql`)

- **The Decks tab.** Personal decks, Alpha-wide decks an administrator publishes, import from a deck file, a card editor, and a review room scheduled by FSRS. **Server state end to end**: nothing touches `AppState` and nothing fires `triggerSync` — a 1,500-card deck inside the synced blob would be re-uploaded on every change. Signing in is required; signed out, the tab is the pitch plus "Sign in to start".
- **Students never see the word "Anki".** The two ways in are **Import a deck** and **Create your own deck**. The importer quietly understands Anki's export (`#separator`, `#html`, `#tags/guid/notetype/deck column` directives) and otherwise reads front, back, tags; only code comments name the app. The **Your decks** shelf is hidden until the student has at least one deck of their own — someone studying only Alpha decks sees the Today hero and the Alpha shelf, and the header keeps both ways in.
- **Three concepts, three places** (`decks.sql` header): ownership is `decks.owner_id`, scope is `decks.scope` (`personal | global`), review state is `user_card_progress` per (user, card). A global deck exists once; ten thousand students are ten thousand progress rows pointing at one card, so an administrator fixing a typo reaches everyone and moves nobody's schedule. Global notes file their previous text in `deck_note_revisions` on every edit.
- **One note is one card, however many blanks it has.** A note with `{{c1::…}}` and `{{c2::…}}` is one `deck_notes` row and ONE `deck_cards` row (`ord` 0, held there by `deck_cards_one_per_note`). It is studied with every blank hidden at once and graded once (`ALL_BLANKS` in `cloze.ts`). This is deliberately not Anki's card-per-cloze model: that turned a two-deck pack into 254 "cards", and a student should not be put off a deck by its size before trying it. Every count (deck totals, today's due, pack and store counts, the console) is therefore a count of notes. The trigger (`deck_notes_sync_cards`) makes the card when the note is written, and no client may write that table. Any edit — words, blanks, even basic ↔ fill-the-blank — keeps the card and everyone's progress. The cloze numbers only tell blanks apart and keep exports Anki-readable. Notes saved under the old model are merged once by `decks.sql`: each student keeps the schedule they reviewed most recently, and their history moves to the kept card. Saved review sessions are versioned (`resume.ts` v2), so a session from before the change is not resumed.
- **Two shelves for Alpha decks: `decks.collection` is `essentials | more`.** Alpha Essentials are the must-haves — featured large, first, and on the first-run screen ("Start with Alpha Essentials"); More from Alpha is a compact grid. It is a biconditional check (`(scope = 'global') = (collection is not null)`, the `poll_visibility` stance): every Alpha deck has a shelf, no personal deck can, and a new Alpha deck lands in `more` unless the administrator picks Essentials (`decks_before_insert` fills it). The shelf is chosen with scope in `AudiencePicker.tsx` — "Who is this deck for?" then, for everyone, "Where should students find it?", each option drawn as the shelf it lands on — on create and import, and changed later from the deck's publishing strip or the console (one-click move, `setDeckCollection`). `deck_summaries`/`explore_decks`/`admin_deck_stats` gained the column and are **dropped before being recreated** (a changed `RETURNS TABLE` cannot be `create or replace`d). `explore_decks` orders Essentials first.
- **Visibility** is `can_read_deck`/`can_edit_deck` (definer). `is_admin()` opens every Alpha deck, drafts included, and **never** a student's personal deck. Lifecycle: `draft` is admins only, `published` is everyone, `archived` leaves the library but students who already had it keep it. A global deck is created only by an admin and only as a draft. Scope and owner are immutable (trigger). The `decks` SELECT policy is spelled out inline rather than calling `can_read_deck(id)`: the function's snapshot cannot see a row inserted by the same statement, so `.insert().select()` would be refused on the deck it just created.
- **Progress and history have no write policies.** `record_reviews` (definer) derives the deck from the card and checks access; it is idempotent on `client_id`, only moves progress forward in time (`reviewed_at > last_review`), and drops a malformed entry in its own subtransaction instead of wedging the outbox. `undo_review` restores `prev`, newest review only. Tested in PGlite: 116 scenarios (12 for shelves) plus planted holes (scratchpad, like the other suites).
- **Scheduling is ts-fsrs** (the one new dependency, lazy with the tab), wrapped by `decks/srs.ts` so nothing else imports it. Learning steps 1m/10m, relearning 10m, fuzz on, retention per deck. Day-length intervals are pinned to **04:00 IST** (`decks/day.ts`), so "due today" means what today means everywhere else. **The intervals on the buttons are computed once at reveal and that exact state is committed** — recomputing on press would re-roll the fuzz.
- **Reviews never wait on the network.** `decks/outbox.ts` writes every answer to localStorage first (per user) and uploads in batches (every 10, every 20s, on hide/online/exit). Undo pops from the outbox if it never left. Sign-out wipes it (`decks/forget.ts`, kept import-free so App's sign-out path does not pull Decks into the main bundle).
- **The card on screen is pinned until it is answered** (`holding` in `session.ts`). `current(session, now)` answers "what is due now", and now moves. Re-asking it on every render let a learning card whose one-minute step had just run out replace the card being studied, even with its answer showing, on any re-render (a save finishing, the rating chip, going online). The rating pressed then landed on the card that had slid in, and the card the student meant came back later unanswered. The pin is kept in state, set during render so there is never a frame without a card, and released only when its card leaves the session in that state. Undo pins the undone card. `answer` removes the answered card by id, never by position.
- **The review room** (`ReviewSession.tsx`): one card on the desk with the rest of the deck stacked under it, the deck's subject colour as light from above, Anki's three counters (new · learning · due). The blank is a **ruled slot sized to the answer** (no dots); on reveal the answer lands on that line, which becomes its underline in the deck colour. Ratings are ignored for 300ms after reveal and reveal for 300ms after a rating (they share one place on screen). **No swipe-to-rate** — a misfire costs days and leaves no trace. Every press floats a "Good · next in 4d" chip off the dock. Keys: Space/Enter, 1–4, Z, E, Esc.
- **The editor never shows markup** (`RichField.tsx`). A cloze is a chip — the hidden words tinted in the deck colour, numbered only so blanks can be told apart — made by selecting words and pressing **Hide**; tapping a chip edits its answer, adds a hint or unhides it. It is contenteditable with discipline: chips are `contenteditable=false` atoms, Enter inserts `<br>`, paste is plain text, the DOM is rebuilt only when `value` changes from outside, and everything entering it goes through the same allow-list as `html.ts`. What it stores is still the portable `{{c1::…}}` HTML that export writes.
- **Card HTML is sanitised at render, every time** (`decks/html.ts`), global content included — the import is not the boundary. Maths is `\(…\)`/`\[…\]` only (not `$`, which in a chemistry deck is a price), with mhchem for `\ce{}`, lazy (`decks/math.ts`). Images live in the private `decks` bucket as `<deck id>/<name>` and cards reference bare file names, exactly as Anki does — so an imported `<img src="benzene.png">` resolves the moment that file is added, and export round-trips.
- **Duplicates**: `content_hash` (SHA-256 of formatting-free, case-kept text) and the file's guid are unique per deck; import skips, never overwrites, and counts within-file repeats too. `import_deck_notes` takes 1,000 at a time and reports inserted/duplicates/failed rather than failing a 2,000-card file on one bad line.
- **Colour is validated** (dataviz validator, both modes, against `#ffffff`/`#141418`): card state is categorical slots 1–3 (never without its number and word — aqua is 2.8:1 on white); ratings are an ordinal blue ramp; mastery is an ordinal **ink** ramp so it never borrows the state colours. `#E10600` stays on actions and progress only. All in `decks/theme.ts`.
- **Every state is designed, the empty ones first.** First run is a hero with a fan of real cards, then Alpha Essentials if any, then a three-step "How it works" with its own small pictures — so launch day, before anything is published, is still a complete page. Nothing due is a hero that says what you did today and when the next card comes; decks with no cards say "add cards", not "no cards". An empty deck is one invitation (Write a card / Import cards) beside an example card in the deck's own subject and colour, plus three tips — never four empty panels. A short row of "Your decks" ends in an "Add another deck" tile that spans the gap, and a short row of Alpha decks ends in "N more decks from Alpha" (scrolls to `#dk-discover`); spans use literal `sm:/lg:col-span-*` strings because CDN Tailwind only sees whole class names. No reviews yet keeps the chart's axis with a line over it. The console with no Alpha decks is a start screen.
- `?decks=debug` is a DEV-only **design board**: every screen and every state of each — full / one deck / only Alpha / all caught up / empty deck, first run with and without Alpha decks, signed out, deck studying / no reviews / empty / Alpha draft, editor, import, create, settings, the Alpha Packs store (stocked and empty), a pack in My Alpha, the pack editor, console with and without decks, review — on fixtures in either theme, nothing written (a dropdown picks the state). `npm run test:decks` runs the pure modules' unit tests (CSV, deck file reading, cloze, hashing, FSRS wrapper, session queue and resume, export round-trip, rack physics, the acquisition state machine, pack geometry) with esbuild + `node --test`, no framework.
- The admin console has a **Decks** section (`admin/DecksAdmin.tsx`, lazy): every Alpha deck grouped by shelf, with status, cards, students, active-in-7-days and again-rate — aggregates only. One visible action per row (Publish for a draft, Publish again for an archived deck); moving shelves, unpublishing, archiving and "open in Decks" sit in the row's menu. Fixed grid columns, the action one included — `auto` is sized per row and the figures stop lining up. Content is edited in the Decks tab; there is one editor, not two.
- **Leaving a session is never starting over.** Every answer is in the outbox before the screen moves on, and the session itself (queue, waiting learning cards, counts) is snapshotted per user and scope after every answer (`decks/resume.ts`, same study day, under 8h). Coming back resumes at "13 / 34". A fresh session lays answers still waiting in the outbox over what the server returns (`applyPending` in `session.ts`), and a learning card that arrives with its step still ahead waits instead of jumping to the front. So a card answered seconds before leaving is never asked twice. `forgetDecksOnDevice` wipes snapshots with the outbox.
- **`MoreMenu` renders through `Overlay`, fixed to its button.** Every Decks card rises in with `mk-rise` (a transform, therefore a stacking context), so an in-flow dropdown painted under the next card and was clipped by rounded lists. That made "Delete deck" and "Import cards" unreachable. The menu measures on open, flips up when there is no room, and closes on scroll/resize rather than drifting.

**Alpha packs** (`decks.sql` §1b and §10, `decks/Packs.tsx`, `decks/PackView.tsx`, `decks/PackSheet.tsx`)
- A pack is a set of Alpha decks studied together ("Physics Essentials" = Kinematics + Laws of Motion + …). Global only and admin-made, with the decks' own lifecycle. **A pack has no shelf**: it is seen only in the Alpha Packs store, on the rack for its `subject` (none means the "More packs" rack; `store/racks.ts` names them). What an admin picks instead is its packaging, `finish` (`ink`/`paper`). The old `collection` column was converted to `finish` and dropped by the migration itself. A deck lives in at most one pack (`decks.pack_id`, ordered by `pack_position`, `decks_pack_global` refuses personal decks). Membership changes only through `set_pack_decks` and publishing through `set_pack_status`, which also publishes the pack's draft decks, so a pack is never half built or published empty. `user_packs` is "this pack is mine". `add_pack`/`remove_pack` keep the pack's decks on the shelf in step, and progress survives a remove. The `decks_pack_fanout` trigger puts a deck published into a pack later onto every owner's shelf. Decks inside a published pack are not listed on their own in `explore_decks`.
- **Ownership is decided by the database, never by a button.** `access` is `free | paid | pro`, and `(access = 'paid') = (price_inr is not null)` is a biconditional check. `pack_unlocked()` (definer) is free, an admin, a `pack_entitlements` row, or Pro while `pro_memberships.active_until` is in the future. It gates `can_read_deck` and the decks SELECT policy for any deck in a pack, so notes, cards, images and reviews of a locked pack are unreadable. A locked pack shows names, counts and three cards (`pack_preview`), nothing more. Neither ownership table has a client write policy. Rows come from definer functions or the payment hook (service role). Adding a free pack records a `free` entitlement, so a pack that later goes on sale stays with everyone who had it. A lapsed Pro closes Pro packs; a bought one stays bought.
- **No payment provider is wired.** `decks/store/checkout.ts` is the seam and currently answers "opens soon" for paid and Pro packs. A provider must write the entitlement (or Pro row) server-side **before** `add_pack` is called, and the opening animation plays only after `add_pack` succeeds. Admins can still price packs. Until payments are live, nobody can take a paid pack, and the editor says so.
- **The pack editor (`PackSheet.tsx`) is built around the object, not a form.** Beside the fields is the pack itself on a hook, drawn by the store's own `PackCard` from what has been typed, with one line under it saying which rack it will hang on. There is deliberately no "where should students find it?" question: decks have shelves, packs do not. On a phone the preview comes first.
- In My Alpha a pack is **an ordinary digital deck** (`AlphaLibraryItem`: cards, reviewed, due, CONTINUE). A pack is studied as one session across its decks: `ReviewSession` takes `deckIds`/`deckInfo`/`resumeKey='pack:<id>'`, new cards from different decks take turns, and reviews go oldest-due first across decks (`interleave` in `session.ts`).
- Tested in PGlite with the deck suite (191 scenarios in all, including the shelf-to-packaging and card-per-blank upgrades, plus planted holes for every gate).

**The Alpha Packs store** (`decks/store/`)
- A physical knowledge store, reached from the store sign in Decks (`StoreEntry`, a short static rack). It is not a card grid. Each subject is a wall with a rack on it (`PackCategory`). The rack is one moving object (`PackRack`: `PackRail`, `HookBack`/`HookFront` per hook, `PackCard` packs). The wall never moves. Packaging is `PackCard` over `geometry.ts`: a die-cut backer, a reinforced euro-slot hang tab, a perforation, and a jagged tear line seeded by the pack number. **Black (`ink`) or white (`paper`) is the admin's choice per pack.** The dark-mode wall is graphite, a step lighter than the page, because black packs on a black wall vanished.
- **Rail → hook → pack is drawn by layering, not by placing a hook behind a card.** The hook's back half (mount plate and rod down to the slot) paints under the pack. Its front half (rod out of the slot and the ball tip with its shadow) paints over it. Packs rotate about the top of the slot (`geometry.pivot`).
- **Physics** (`physics.ts`, pure and tested): drag is 1:1, with a 6px threshold. Release velocity comes from the last 90ms of the finger. **Every throw is one glide** (iOS's exponential decay, τ = 325ms) that leaves at the finger's speed and arrives at rest exactly on its landing point. That point is the hook ahead nearest v·τ, or the end of the rack if the throw would run off it. **Nothing switches curves mid-motion.** A capped "bump" off the end, and a spring onto a nearby hook carrying the throw's speed, both made the rack stutter before stopping on short racks, where nearly every throw reaches an end. **The ends are firm**: pulling past one gives at most `MAX_OVER` (64px, whatever the screen width), and letting go there returns on a stiff critically damped spring with no bounce. Trackpad momentum against an end springs back as soon as the push fades. Mid-rack, trackpad scrolling stops where its momentum ends: no snap to a hook afterwards, which was a second, sometimes backwards, motion. Each pack is a damped pendulum driven by the rack's smoothed acceleration, capped near 3.4°. Vertical wheel and vertical swipes (`touch-action: pan-y`) stay with the page. A tap on a gliding rack only catches it. **A gesture never re-renders React**: one rAF loop writes `transform` to the track and to each pack, and runs only while something moves.
- **Taking a pack is a state machine** (`PackAcquisition.ts`, tested): IDLE → SELECTED → ACQUIRING → DETACHING → CENTERING → TEARING → REVEALING → TRANSITIONING → ACQUIRED. Every event that does not fit the phase returns the same state, which is the whole defence against double taps, a second pack mid-flight and duplicate unlocks. ACQUIRING is the server's turn. The opening (`PackOpeningAnimation`, WAAPI on transform/opacity, about 3.4s the first time and 3.1s after: slow on purpose, mostly the tear) starts from where the pack hung. It reports each phase boundary back. The order is take, carry to centre, a beat, tear from the slot down and along the perforation, flap folds away, three real cards rise and fan (`PackReveal`), the packaging falls away, then "✓ ADDED TO ALPHA", then the pack's page. Reduced motion skips straight to the confirmation, and the racks lose their sway.
- **The detail panel opens under the rack, not in a modal**, with a caret held over the lifted pack by the rack's frame callback. It stays mounted through the opening, because unmounting it shifted the page under the pack in flight. **A hook holds a stack, and a rack never empties.** Behind every pack, two more copies peek out further back on the rod (`PackStackEdges`). They are dark, blurred and outline-free, so the front pack is the only crisp object; outlined copies made the rack look busy. They are flat silhouettes with no text or gradient, inside the sway layer, so they cost nothing per frame. A pack you own stays on the rack: the next copy shows, further back on the rod, darkened and slightly out of focus (`--pk-rear`), with a crisp "In My Alpha" badge that opens it. The same copy appears the moment a pack is taken and flies off. A rack with at least one published pack ends in dashed **Coming soon** slots (`PackSoon`), filled up to four hooks with at least one. A subject with nothing published gets no rack at all.
- The store is its own lazy chunk (~14 kB). `?decks=debug` → "Alpha Packs — store" runs it on fixtures, with a "Pro + bought" switch and Restock. The browser pane renders frames only while visible, so verify the opening by seeking animations, not by timing screenshots.
- Run order: `admin.sql` before `decks.sql`.

### Alpha Notes (`notes/`, `supabase/notes.sql`)

- **The Notes tab: a notebook for JEE that replaces Notion/Obsidian**, local first. Pages nest, a page has a body of blocks (headings, lists, to-dos, toggles, boxouts, pull quotes, tables, code, images, dividers), and the maths is native: `$…$` becomes an inline equation as you type, `$$` and a space a display one, KaTeX with mhchem (`\ce{}`) lazy in `editor/katex.ts`. `@` mentions a syllabus chapter (a chip in its subject's colour carrying its live status), `[[` links a page (or makes one), `/` opens the block menu. A to-do can be sent to the Today board ("→ Today", `TodayTasks` in `editor/nodes.ts`, via App's `addTask`). Markdown pasted or imported (Obsidian, Notion exports, a ChatGPT answer) is parsed with TipTap's Markdown extension; `editor/markdown.ts` lifts `$…$` out before parsing (Markdown would read the `_` and `*` inside as emphasis) and puts equations back after. Copy as Markdown exports the same way.
- **Opt-in, behind a cover page.** Until the student turns Notes on, the tab is `Cover.tsx` and nothing else: no IndexedDB is opened, no Yjs or TipTap is downloaded (the cover chunk is ~3 kB JS), nothing syncs, and Syllabus shows no `+ Notes` link. `NotesTab.tsx` is only the switch: it sets the palette, draws the cover or lazy-loads `NotesWorkspace.tsx` (the workspace, named so because macOS resolves `./Workspace` to `workspace.ts`, the page tree). The decision is `AppState.notes = { on, at }` (`notes/pref.ts`), a dated decision rather than a flag because App's local-newer merge spreads the remote blob over the local one; all three merge paths keep the later one (`mergeNotesPref`), so turning it on once reaches every device. **Turning it off** (Pages panel → Turn off, with a confirm) shows the cover again and deletes nothing.
- **The cover is a product page** (`cover.css`): a hero (New in Alpha, "Notes." with the red stop, "The notebook that knows JEE.", one red Turn on Notes button), a tilted product shot of a real page with the pieces only Alpha has floating off it (a chapter mention with its status, a to-do already on Today), then **"Why not Notion or Obsidian?"** as a bento of what only Alpha does: it knows your syllabus, to-dos go to Today, maths as you type, one app, works offline, imports your Markdown; and the button again. Every picture is hand-built HTML/SVG in the app's colours (the landing page's rule), the formula is hand-set so the cover never loads KaTeX, and the mock-ups use real chapter names. **Say nothing about other apps but what they are for** ("built for everything"): their prices and features change, and a cover that is wrong about a rival is a cover nobody trusts. Every claim about Alpha must stay true. The bento sizes by its own width (a container query), because the rail takes a share of the window.
- **Design: quiet, Apple-like, and Alpha's own.** Two rounds got here. The first read as a Notion clone (emoji page icons, "Add icon", a page card, a `+ ⋮⋮` handle, boxed glyph tiles). The second, a "printed page" (mono kickers, bylines, double rules, margin section numbers, equation and figure numbers), read as overloaded. What stands now (`notes/notes.css`, hand-written and scoped like the reader's): **say each thing once and let whitespace do the rest.** Interface text is Satoshi in sentence case; what the student writes is **Literata** ("Book", the default face; Sans and Mono per page); mono only for code and shortcuts. **Home** is the large title "Notes." (the one red full stop) and the pages, grouped by subject (a coloured dot and its name), each row a title, a date and one line of preview: no buttons (New page and Search live on the pill, Import in the Pages panel), no counts, no numbers. **A page** is a quiet toolbar (‹ back to the parent, pin, •••), a small subject tag only when the page belongs to a chapter, the title, and a Playfair summary line (`PageMeta.dek`) that is hidden while empty and shows itself only when focused (Enter from the title, or ••• → Add a summary). Word count, typeface, width, move, export live in the ••• menu. Boxouts are soft tinted panels with their kind in its colour, tables are rules, bullets are small dots, the highlight is a marker stroke, the selection bar is inverted ink. **Formats are offered where the choice is made**: under the title of a new, empty page ("Or start with", drawn as wordless hairline sketches, `Sketch.tsx` from `Template.sketch`) until the first word is written, and on the home screen only while the notebook is empty. **A page is marked by its subject's colour** (`pageSubject` in `workspace.ts`: its chapter, an ancestor's chapter, or a subject-named folder), never an emoji; `PageMeta.icon` survives only so old data reads. Before adding a label anywhere in Notes, check whether space already says it. `#E10600` is spent on the home title's full stop, the caret and the drop line.
- **Navigation is its own liquid glass pill, bottom centre** (`WorkspaceBar.tsx`): Pages · Search · Home · New page, apart from Alpha's rail. Bottom centre because every other edge is taken (capsule top, class switch and gear right, rail left); on a phone it is icons only, between the feedback launcher and the gear. Pages raises a glass panel above it with the tree (`NotesNav.tsx`: favourites, the page tree with drag to nest or reorder, trash, import, sync state). The panel and the pill are **siblings, not nested**: the pill steps aside with a transform while you write (on a laptop until the mouse moves; on a phone the editor's own bar takes the bottom edge while the keyboard is up), and a transform on an ancestor would become the containing block of a fixed panel. Centred by margins (`left/right` + `margin: auto` + `fit-content`), never by a transform, which would fight `lg-pop`. The pill uses `chroma` (see the design system): two iridescent crescents at its corners.
- **Opening Notes collapses the rail** and leaving restores it to however it was (`railBeforeNotes` in `App.tsx`, above every early return): Notes is a writing room. `<main>` keeps its width; the page measure is 680px (960 when the page is set Full width).
- **Local first, for real.** Every page lives in **IndexedDB** on the device (`notes/store.ts`, one database per owner: `alpha-notes-guest` or `alpha-notes-<uid>`), never in `AppState`: a notes blob there would be re-uploaded whole on every keystroke and every merge path in App would have to learn it. Each page body is a **Yjs document**, so two devices editing offline merge without losing either's words; the tree is one more Yjs document (`workspace`), a map of pages whose fields merge independently. A purge is a tombstone (`deleted`), so an offline device cannot resurrect a page by editing it. Saving is debounced off the keystroke (400 ms), `REMOTE`/`LOAD` origins never echo back out, and writes per document are serialised (`lock`) so a pull merging into a closed page cannot race the student opening it. **The store is shared and reference-counted** (`acquireStore`/`releaseStore`): leaving the tab writes everything to disk at once and closes only after a minute unheld. Closing it on every unmount closed it under an editor still typing in development (effects re-run on hot reload) and lost words; it also makes returning to Notes instant.
- **Sync is Supabase, only when there is another device** (`notes/sync.ts`, `supabase/notes.sql`): Postgres is the mailbox, Realtime the doorbell. The outbox (`push.ts`, no Yjs, so sign-out can flush it without the editor) sends one row per page per burst of typing to `note_updates` (base64 Yjs updates; the server never reads them). Pull reads rows from other origins since a **server-timestamp cursor re-read with a 60 s overlap** (an identity id is not a commit order; re-applying a Yjs update is a no-op). A Realtime INSERT from another origin is applied at once. **Compaction** (`compact_note_doc`, security invoker) replaces a page's rows with its full state once it has gathered 150, deleting only rows older than everything the compacting device has certainly seen. The origin belongs to the database, not the device, so a wiped database pulls its own old rows. The `created_at` cursor is set by trigger, never by the client; a flood guard caps 600 rows a minute. No `is_admin()` anywhere: staff cannot read notes. **Images** are compressed on the device (`files.ts`, WebP or JPEG, ≤1600px) and stored in the private `notes` bucket as `<uid>/<id>.<ext>`, never inside a document. Run `notes.sql` any time; until it is run, sync shows "Saved on this device" and everything else works.
- **Guests have the whole feature**, nothing leaves the device. **Signing in adopts guest notes into the account** (`adoptGuestNotes`: pages, bodies, images; ids are random, so the workspaces merge as maps) and deletes the guest database. **Sign-out** pushes the outbox first (`flushNotesBeforeSignOut`, bounded to 4 s), then closes every open notes connection (a blocked `deleteDatabase` may never finish on a page about to reload) and deletes the account's database (`forgetNotesOnDevice`, kept import-free in `notes/forget.ts`). Account deletion empties the `notes` bucket folder first (`account/deleteAccount.ts`). Purging a page also deletes its server rows.
- **Syllabus ↔ Notes.** Every chapter card on Syllabus has `+ Notes` / `Notes`; it opens that chapter's page or makes one from the Chapter notes template inside a subject folder (`NotesRequest` in App). Syllabus cannot open Yjs, so the Notes store writes a tiny `chapterKey → pageId` index to localStorage (`alpha_notes_chapters_v1:<owner>`) for it to read.
- **Templates are written straight into Yjs** (`editor/fill.ts`: the schema from `contentExtensions` and `prosemirrorJSONToYXmlFragment`), never through an open editor, and only into an empty page, so they cannot duplicate across devices. Same path for Markdown import.
- **Performance.** The tab is lazy (App), and the editor is lazy again inside it (`PageView` lazy-loads `NoteEditor`), so the home screen arrives without TipTap: keep the page chrome off `editor/*` imports (the status colours live in `notes/status.ts` for exactly this reason; importing them from `editor/nodes.ts` pulled TipTap into the tab's first chunk, 46 → 152 kB gz). `shouldRerenderOnTransaction` is off: a keystroke re-renders nothing in React. Node views (equations, chips, page links, images, boxouts) are plain DOM, not React roots. **TipTap's React `BubbleMenu` re-dispatches a transaction whenever a prop changes identity**, so its `shouldShow` is module-level (`showBubble`) and the bar redraws on `selectionUpdate`/`update` only; an inline predicate plus a redraw on every transaction looped forever ("Maximum update depth exceeded") while any page was open. The page gets the editor from an effect on the instance, never `onCreate`: under StrictMode the first instance is destroyed and `onCreate` handed over the dead one.
- **Block commands lift the line out of a list first** (`clearNodes()` in `editor/blocks.ts`): a boxout or heading cannot sit as a list item's first child, and without it "/" → Boxout inside a bullet failed silently.
- Tests: `npm run test:notes` (the tree, tombstones, two devices merging offline, search text, Markdown maths). The browser tool's typing inserts text in a way that skips ProseMirror input rules: test `$…$` through `view.someProp('handleTextInput', …)`. A live editor keeps the extensions it was built with, so reload after editing anything under `notes/editor/`.

### Shareable stats (`share/`)

- Three cards — **Daily** (near-black), **Weekly** (warm cream), **Monthly** (deep forest green) — rendered as PNGs from real logged data and pushed out through the OS share sheet. Reached from a `ShareButton` on **Streak** (opens on the week) and **Today** (opens on the day).
- **Canvas 2D, drawn imperatively, zero dependencies.** The two alternatives both fail on this stack: a DOM screenshot (`html2canvas`) inherits the browser's rasterisation and reimplements CSS badly, and an SVG loaded into an `<img>` **cannot load an external font** — every line of type would silently fall back unless the woff2 were base64'd into the string. Canvas gives exact pixel control at any resolution, and **fonts never taint a canvas**, so Satoshi coming from a third-party CDN is not a CORS problem.
- **The preview *is* the canvas.** `useCardImage` hands `ShareModal` the same `HTMLCanvasElement` that produced the blob, CSS-scaled. There is no second HTML rendering of a card to drift, so what the user approves is byte-for-byte what leaves the device. The corollary: the node holding it must have **no React children** — React and `replaceChildren` cannot both own a parent, and when they try React throws `NotFoundError` on the child it no longer finds. The loading and error states are siblings for that reason.
- **`navigator.share` needs transient user activation, and an `await` spends it.** Rendering or encoding inside the click handler makes iOS Safari throw `NotAllowedError`. The blob is therefore encoded alongside the preview and `onPrimary` is deliberately not `async`.
- **There are no Instagram or WhatsApp buttons, and there must not be.** Neither is reachable from a web page: Instagram's Stories path needs a native app with a registered Facebook App ID writing to the iOS pasteboard, and `wa.me`/`whatsapp://` carry text only. The OS sheet lists both and is the only real integration that exists. Capability is probed with an actual one-byte `File` through `navigator.canShare` — never a UA check, because desktop Firefox and Chrome-on-Linux have `navigator.share` and reject files. The one place a UA check *is* correct is `saveCard`: iOS Safari ignores `<a download>` for blob URLs, which is a rendering quirk with no feature to detect, so it opens a tab and the UI says to long-press.
- **`share/stats.ts` is pure and is the only place arithmetic happens.** `render/*` receives labels and rounded numbers and asks the data no questions — a canvas layout that also computes is one nobody can adjust.
- **Counting stops at today; drawing does not.** `lived()` clamps every aggregation to days that have happened, so a clock-skewed device cannot produce `27/07 DAYS ACTIVE`. The week still draws seven bars and the month still draws all its dots — the empty tail is the period still being written. The bars specifically are built from the *counted* range: a chart summing to visibly more than the hero above it is the one contradiction a shared card cannot survive.
- **Comparisons are like-for-like.** An in-progress month measured against a *complete* previous month reads as a 70% collapse on the 7th, which is arithmetically true and useless. The previous period is read over the same number of elapsed days, clamped to its own length so a 31-day month never reaches past the end of a 28-day one. No previous period, or a previous period of zero, drops the slot entirely — `0%` claims a flat week that never happened and `—` looks like a bug.
- **The second metric is a fallback chain, not a field**: tasks → questions → sessions (daily stops before sessions, which it already prints). `Task.completedAt` only exists going forward, so an account with months of history can have no dated completions at all; the label travels with the value so the card can never announce the wrong noun.
- **Type is Satoshi + Playfair only** — the app's own faces. `fonts.ts` asks for **900, not 800**: the mirror serves 300/400/500/700/900, so `fonts.check('800 …')` answers *true* for a weight that does not exist and the verification would be meaningless. The Monthly hero is Playfair 700 — the reference's monthly figure is a serif, and it gives that card its own identity without a new colour or layout. Every hero goes through `fit()`, which is also the entire font-fallback strategy: a wider fallback face fits by the same mechanism instead of running off the card.
- Three **real compositions** in `render/format.ts` (4:5 / 9:16 / 1:1), not one scaled three ways — 9:16 redistributes the vertical space and carries deep safe margins so Instagram's chrome never lands on the work. Exported at 2× (2160px wide).
- `#E10600` appears on **no card**. The accent belongs to actions and to the now-line, the same reservation `schedule/colors.ts` makes. The `@lockedinshreyash` invitation lives in the modal and never on the artifact.
- Phrase selection (`phrases.ts`) is **deterministic** on the stat state — a caption that reshuffles per render turns the artifact into a slot machine, and the user notices the second time they open the sheet.
- **The app's only lazy boundary.** `React.lazy` on `ShareModal` keeps the renderer out of the main bundle (~23 kB separate chunk). Nothing in the share flow writes `AppState`, so no card ever fires `triggerSync`.
- `share/DebugCards.tsx` is a dev-only contact sheet at **`?share=debug`** — every period × every format × seven fixtures (zero, first period, legacy tasks, extremes, February) on one page. Gated on `import.meta.env.DEV` and tree-shaken out of production. It is how the compositions get compared against the reference; "it renders" was never the bar.

### Task board (`board/`)

- The Today tab's task list is a **three-column board** — Todo → Doing → Done — replacing the old flat `TaskSection` grid. `board/board.ts` is pure and React-free (same contract as `schedule/schedule.ts`); `board/TaskBoard.tsx` is a zero-logic container taking a narrow slice plus narrow callbacks, like `schedule/PlanTab.tsx`.
- **`completed` stays authoritative, `column` is written in lockstep.** `share/stats.ts` counts `completed && completedAt`, and every task saved before the board has nothing else. `moveCard` is the *single* code path that writes `completed`/`completedAt`/`column`, and `toggleTask` routes through it — otherwise two paths could disagree about the same card.
- `normalizeTasks` (`state.ts`) is new: there was no task normalizer before, and the board cannot tolerate a missing `column`. It derives one from `completed`, forces the two to agree when a sync merge produces a row where they don't, and backfills `order` per column by array position so a legacy list opens in the order it was written.
- **Ordering is a stored `order`, reindexed 0..n on every drop** — not fractional ranks. A board holds tens of cards, and a whole-column reindex also repairs the duplicate orders a sync union can leave behind. Sorting falls through to the id so two devices resolve ties identically.
- Drag copies `schedule/DayTimeline.tsx`'s discipline wholesale: **a gesture never touches `AppState`** (one commit on release, not ~60 upserts per drag), Pointer Events with listeners on `window`, a `gesture` state to wake the binding effect, a movement threshold, and `suppressClickRef` so the trailing click does not open the editor on the card just dropped. What differs is the arithmetic — a column/index hit test instead of pixels-to-minutes — so `board/useCardDrag.ts` is written fresh rather than extracted from a working gesture that has no columns in it.
- Two rules exist for a cheap phone: pointer moves are **coalesced into one `requestAnimationFrame`**, and **every rect is measured once at `pointerdown`** (`getBoundingClientRect` in a move handler forces synchronous layout every frame). The dragged card moves by `translate3d` only, with `will-change` on that one card and removed on release.
- **`React.memo` on the board is load-bearing, not decoration.** `today/TodayTab.tsx` runs a 100ms interval while a stopwatch is going, so the tab re-renders ten times a second through every session. The board's App-level mutators are therefore `useCallback([])`, and `activeSubjects` is memoised — `getActiveSubjects` returns a fresh array literal per call, and an unstable array there silently defeats memo on every child that receives it.
- Mobile is horizontal **scroll-snap** columns at ~82vw with edge autoscroll during a drag; three columns on a 375px screen is unusable. Done shows the most recent `DONE_VISIBLE` with a "+N earlier" expander — a Done column with 200 cards is a wall, and arriving in it is the point of the column.
- **Card colour is subject-tinted by default with a per-card hex override**, dispatched exactly like `blockStyle`: `taskStyle` reuses `derive` and `subjectStyle` from `schedule/colors.ts`. `SUBJECT_COLORS` stays fixed — the override is the user's own label, and it never rewrites what Physics-blue means elsewhere. `PRESET_COLORS` moved into `schedule/colors.ts` so the palette and the card picker share one list. Every colour is an inline `style`; CDN Tailwind compiles `bg-[${hex}]` to nothing.
- **Deadlines are a field on `Task`, not a separate entity.** `dueAt` is a study day; `dueMinute` is on the **study-day axis** (0 = 04:00), the same axis as `ScheduleBlock.start`, so `toClockValue`/`fromClockValue` bridge it to an `<input type="time">` with no new conversion code. Absent `dueMinute` means "use `ReminderPrefs.defaultMinute`", so moving that default moves every task that never asked for a time and none of the ones that did.
- The card's due label is **calm and deliberately not a countdown** — "DUE SUN", "DUE TOMORROW", and past it "OVERDUE" in the accent. A live shrinking countdown on every card is a pressure users tune out inside a week.
- **Task → plan link**: `ScheduleBlock`/`TemplateRule` carry an optional `taskId`, and `BlockEditor` offers a task picker on study kinds. `blockTitle(block, taskText)` takes the resolved text as an argument — `PlanTab` builds the map and passes it as **display text**, never writing it onto the block, because the editor reads `label` back off the block when it opens and would save a borrowed title as a real one. `normalizeSchedule(raw, knownTaskIds)` drops links to deleted tasks (App's load path is the one place with both halves in hand). Deliberately one-directional: finishing a block does not tick the task, because sitting down to work on something is not finishing it.
- Session history on Today is **collapsed by default** behind a header carrying the count and hours. Local `useState` — a disclosure preference is not data, and in `AppState` it would fire a Supabase upsert every time somebody opened it.

### Notifications (`notify/`) and reminders (`reminders/`)

- **The product rule moved and changed.** `leaderboard/notify.ts` used to open with an absolute law: a notification reports a race that is actually happening, or it is nothing. That rule now lives at the top of `notify/channels.ts` with its real boundary: **the app never invents a reason to interrupt you; it may hold you to something you wrote down yourself, or, if you asked for it, remind you once a day of a time you chose, only on a day you haven't finished.** A deadline you typed on a date you chose is allowed to speak. Digests and "you haven't opened the app in three days" are still forbidden. `leaderboard/notify.ts` keeps a race-scoped header pointing here.
- **Daily nudges (`reminders/nudges.ts`, the `nudge` channel) are the one opt-in exception, chosen deliberately for retention.** The student picks a study time (onboarding's `Reminder.tsx` or Review → Daily nudges); then up to three a day on the study-day axis: **start** at their time if nothing is logged ("TIME TO LOCK IN · Day 13 starts now"), **goal** at an evening check (`goalMinute`: start + 3h, clamped to 8–10 PM) if the goal isn't met ("7.5H TO GO · Only 7.5 hours left of your 10-hour goal. The day is not over yet."), and **last** at 11 PM if nothing is logged and a streak is at stake (wording changes when firewood would hold it). A goal met silences the day; a running session silences it (marked handled, never said); all three share one lock-screen tag per day. `nudges.ts` is pure (hours, streak, bank, `instant` passed in); `nudgeState.ts` builds the input from AppState with `streakLedger(logs, { today: day })` per day ahead, so firewood burns are projected. **The client decides everything, as for deadlines**: `nudgeRows` publishes today plus `NUDGE_DAYS_AHEAD` (3) days into `due_reminders` as `nudge:<kind>:<day>@<instant>`, recomputed on every log (copy carries the live numbers; meeting the goal withdraws the rows). A student who stops opening the app runs out of published days and goes quiet in four days, with no server rollover and no server read of their data. **Tasks and nudges go through ONE reconcile** (it deletes every unsent row it was not handed), and the publish effect is not gated on the switches, so turning nudges or push off withdraws what is queued. Locally `useNudges` (App root, beside `useReminders`) says the latest due slot within `NUDGE_STALE_MS` (20 min) via `deliver`, and appends handled keys to the synced `ReminderPrefs.nudged` (bounded `NUDGED_KEEP`), which the publisher excludes, the `remindedKey` arrangement. Guests get local nudges; push needs an account, and App arms push on sign-in when nudges are on and permission is already granted. The sender tags `nudge:` rows per day, non-sticky, `channel: 'nudge'`, URL `/?open=today`; `sw.js` passes `channel` through (worker `push-offline-v3`). **The edge function must be redeployed** for the per-day tag. `npm run test:nudges` (12 tests).
- **One `showNotification` call site** (`notify/system.ts`), replacing two duplicate `new Notification` calls. It **prefers the service worker registration over the constructor** — that is a correctness fix, not a preference: Android Chrome throws on the constructor outright, so the Pomodoro bell had never once rung on a phone, the only device where a backgrounded bell matters.
- `notify/deliver.ts` routes one event to exactly one place: seen → dropped, visible tab → toast, hidden tab → system notification, closed app → push. Never two.
- `notify/toastBus.ts` is a **module-level bus, not a context**. Half the callers are not components (the Pomodoro bell fires from inside a `useCallback`, the reminder engine from a window handler), and a context whose value changes per toast would re-render every consumer under App's single `state` — a nine-second countdown paid for by the timeline and the heatmap. `ToastHost` is the only subscriber and renders `null` when empty, which is almost always. Auto-dismiss clocks **pause while the tab is hidden**, or a toast pushed just before a tab switch burns its nine seconds unseen — precisely the case `deliver` chose a toast for.
- `RaceToast` was migrated onto the bus.
- `reminders/reminders.ts` is pure. Its central idea: **almost every cancellation is a filter, not an operation.** Ticking a task off, clearing its date, or deleting it all stop its reminder because the scan stops selecting it — there is no `cancel()` and therefore nowhere to forget to call it, which matters because tasks are mutated from App, the board and the sync merge.
- `Task.remindedKey` is **the fire key, not a boolean**. The key contains the due instant, so moving a deadline re-keys and re-arms it by itself. It rides the synced blob deliberately: a reminder fired on the laptop must not fire again on the phone.
- `reminders/useReminders.ts` is mounted at App root beside `usePomodoro`, for the reason that hook documents — an engine inside a tab component stops existing when the user opens another tab. It mirrors the same discipline: wall-clock derived, idempotent per fire key, `ready` gated on the initial cloud pull (a pull replaces `tasks` wholesale and would otherwise discard a `remindedKey` and double-fire), and a mount pass that **is** the catch-up-on-reopen path rather than separate code.
- **One timeout for the whole board**, armed at the earliest pending instant — not one per task. The 30s safety interval only runs when something is within the hour; a user whose next deadline is in December arms **nothing at all**.
- A reminder more than `STALE_REMINDER_MS` (12h) overdue is **marked silently and never shown** — telling somebody at 4am about a 4pm deadline is an accusation, not a service, and the card already reads OVERDUE. Past `MAX_BURST`, fires collapse into one line.
- **Never the same reminder twice**, via four independent mechanisms: `PUSH_LAG_MS` (90s) so an open app always fires first and deletes its own row; that row deletion; the IndexedDB ledger in `notify/seen.ts`, shared with `public/sw.js` (IndexedDB rather than `localStorage`, which does not exist in a service worker — the one context that most needs to ask); and the per-task `tag`, which makes even a true double-show replace rather than stack.
- **`public/sw.js` is push plus a navigation-only offline fallback — and nothing else.** It had no `fetch` handler at all, on the reasoning that one sits in front of every request forever; that reasoning was about a *caching* handler and still holds. What forced the change is that **Chrome fires `beforeinstallprompt` only for a page whose worker has a `fetch` handler** (since Chrome 108/112 a worker is no longer needed to install from the browser menu, but the prompt still requires one), so the app was structurally uninstallable and the Install button had never once rendered. The handler therefore intercepts `request.mode === 'navigate'` and returns immediately for everything else — scripts, styles, fonts and every Supabase call never reach it. It is network-first with the cache consulted only in the `catch`, so a deploy can never be shadowed by a stale shell, and the single cached entry is `offline.html`, versioned with the worker. Chrome's own guidance warns against the empty no-op handler people add to satisfy this check; an offline fallback meets it with something the user gains from. Registration is `/sw.js` with an explicit root scope; a relative `./sw.js` resolves against the *page*, so a deep link would register a narrower scope and pushes would never arrive.
- `reminders/publish.ts` is a **reconciler, not per-mutation calls** — the desired row set is a pure function of the tasks, so every cancellation falls out of the diff. Debounced, and skipped on an unchanged signature (`rewards/engine.ts`'s no-op contract applied to a network call). Dynamically imported, as is `notify/push.ts`: a user who never enables push downloads neither.
- `supabase/reminders.sql` holds two narrow tables, **deliberately not `user_profiles`**. The sender runs as the service role and bypasses RLS entirely, so if it read that jsonb blob it would be a cron job with unrestricted access to every user's private life, running every minute, forever. The client decides what is due and publishes only the two strings it wants read back to it. Same reasoning `leaderboard.sql` gives, with sharper stakes.
- The Edge Function **claims before sending** (`update … set sent_at where sent_at is null returning *`). The trade-off is stated in the code: claiming first can lose a reminder on a crash, sending first can duplicate one. The rule is "never twice" — a lost reminder is a disappointment, a duplicated one is why people turn notifications off.
- Deploy is user-run and documented in `supabase/functions/send-reminders/README.md`. The feature ships dark until then: without `VITE_VAPID_PUBLIC_KEY` the closed-app switch does not render at all.
- Install lives in `install/useInstall.ts` (the quick-settings row and the mobile banner share it). This matters because **iOS delivers Web Push only to a PWA installed to the home screen**. See the PWA install section below.
- **Two push bugs were latent until the feature was first deployed**, both silent because nothing had ever exercised them. `notify/push.ts` read the subscription keys with `getKey()` and re-encoded them with `btoa` — standard base64, where every push server expects base64url; it now takes `subscription.toJSON().keys`, which the browser already publishes correctly encoded. And the Edge Function passed the two VAPID env **strings** straight to `importVapidKeys`, which takes `JsonWebKey` objects, so it would have thrown inside `crypto.importKey` on its first run; `vapidJwks()` now splits the 65-byte uncompressed P-256 point into the `x`/`y`/`d` a JWK wants.

### Administrators, announcements and feedback (`admin/`, `announce/`, `feedback/`)

- **One predicate, defined in the database, referenced by everything.** `public.is_admin()` (`supabase/admin.sql`) is `security definer` and answers only about `auth.uid()`, taken from the verified JWT. Every policy and every admin RPC references it, so there is one definition of "administrator" and nowhere for a second to drift. `security definer` is also what stops the recursion of a policy on `user_roles` that calls a function reading `user_roles`.
- **The client is never a security boundary.** `admin/useAdmin.ts` decides whether the Admin tab is *drawn* and nothing else. Forcing it true in devtools yields a console whose every query the database refuses. The role is asked of the server rather than read from `AppState`, because that blob is client-written — a role kept there would be a privilege the client could grant itself from localStorage. For the same reason `user_roles` has **no insert/update/delete policy at all**: under RLS that denies those operations to every client, and the only writers are `grant_admin`/`revoke_admin`, which check `is_admin()` as their first statement. The first administrator is one statement in the SQL editor (`supabase/admin.sql` §7) — a first-run "claim this app" screen is a race anybody who finds the deploy can enter. `revoke_admin` refuses to remove the last one.
- **`announcements`, not `notifications`.** `notify/` already means OS-level notifications here — a Pomodoro bell, a deadline on a lock screen. These are the opposite: one row, written once by a human, read by everybody. Sharing the word would guarantee somebody wires up the wrong one.
- **One global row, per-user acknowledgement.** Publishing fans out to nobody; `announcement_reads` is keyed `(announcement_id, user_id)`, and that composite primary key **is** the deduplication strategy — a double tap, a retry after a dropped connection and a second device all upsert the same row. A `read` boolean on the announcement itself would mean the first student to acknowledge it hid it from everyone.
- Publication is `published_at`, not a boolean: a timestamp answers "is it live" exactly as well and also answers "since when", which is the first thing anyone asks about a notice that went out wrong. Null is a draft, a future value is scheduled, and the SELECT policy — not a client-side filter — is what keeps both invisible. `announce/api.ts` re-filters on top of it anyway, because an **admin's** select policy deliberately returns drafts so the console can list them.
- **It appears on Today, and only on Today.** `useAnnouncements(user, activeTab === 'Today')` is the whole trigger: a forced check on arrival, a throttled one when the tab is foregrounded, and nothing else. No realtime subscription — `user_profiles` has one because a stale AppState on a second device is actively wrong, whereas an announcement arriving four minutes late is not. `supabase/admin.sql` §8 has the one line that adds it if it is ever wanted.
- **Closing is not reading.** Only the explicit button acknowledges; the scrim and Escape set the notice aside, and Today then shows a `NoticeLine` to reopen it. An announcement lost to a stray tap is an announcement that never went out. Multiple unread are walked **sequentially**, oldest first, with "1 of 3" and a "Mark all read" that only appears when there is a backlog — the same stance `UnlockModal` takes on pending rewards.
- `notify/NoticeLine.tsx` is the sleep nudge's pill, **generalized rather than copied**. Its reasoning transfers exactly: Today is for what you need to do today, so a thing that lives somewhere else gets a line and not a card. `analysis/SleepReminder.tsx` keeps only the part that is about sleep — when to show it, and what dismissing it means.
- The modal is built on `UnlockModal`'s shell (same scrim, radius, entrance, footer) because those two (plus the daily streak moment, built on the same shell) are the only things allowed to stop you on arrival, and two interruptions that look different are two interruptions. `#E10600` is spent on the `important` type alone; a broadcast that arrives in the action colour every time teaches people to stop reading it.
- **Six announcement types, and two of them carry data.** `poll` and `video` were added after the first four. A video is one string, so it is one column (`video_id`, the 11-character YouTube id and never a URL — the value reaches an iframe `src`, so the database validates its shape in `announcement_video_shape` and the client extracts it from whatever link was pasted). A poll is a list you vote against, so it is two tables: `announcement_poll_options` and `announcement_poll_votes`.
- **Nobody ever reads another person's vote — not students, not administrators.** The votes table's SELECT policy is `auth.uid() = user_id` with no admin clause at all; results exist only as aggregates from `poll_results()`, a definer function counting rows no client may select. There is deliberately no endpoint that joins a person to an answer. That is a decision about minors' data, and it is why `private` visibility means "the tally is for staff", not "staff can see who said what".
- `poll_visibility` is `private` | `live`, enforced by a **biconditional** check (`(type = 'poll') = (poll_visibility is not null)`): a poll must declare one and nothing else may carry one, so changing a type cannot leave a stale setting the UI no longer shows but the results function still acts on.
- **Every reference in the vote policies is fully qualified, and it has to be.** `announcement_poll_options` has an `announcement_id` column of its own, so an unqualified `announcement_id` inside those subqueries binds to the *inner* row and the guard degrades to `o.announcement_id = o.announcement_id` — always true, letting a crafted request vote on this poll with an option belonging to another.
- **"Has answered" and "can see the tally" are two separate states in `PollBody`, and conflating them was a real bug.** The answered view was originally gated on the poll being `live`, so voting in a PRIVATE poll changed nothing on screen: the row was written, the student was looking at the same buttons they had just pressed, and a write with no acknowledgement is indistinguishable from a broken button. There are now three views per option — a button (unanswered), a locked row with the choice marked "Yours" (answered), and a bar (answered **and** live **and** the tally has arrived). Every poll confirms; only a live one explains. Bars additionally require `tally !== null`, because the old code drew every option at 0% when the tally call was refused — a chart contradicting the vote just cast.
- The tapped row says **"Saving…" on itself** before the request returns rather than every row greying out together, and an answered poll offers **Change** (the `(poll, user)` primary key means changing your mind is an UPDATE of the row you already own). A poll you cannot correct on a phone is a poll whose first accidental tap is final.
- **Tapping an option selects it; the modal's primary button is Submit.** The footer used to show a big red "Skip" under an unanswered poll while a tap on an option was the vote itself — people pressed Skip thinking it was how you answer, and response rates collapsed. Skip is now a small underlined text link in the header (it still marks the notice read), and Submit stays disabled until something is picked. `PollBody` reports `{open, draft}` up via `onStatus` and exposes `submit()` through a ref. A private poll's Submit also acknowledges and moves on; a live one stays open on its results with "Got it".
- **Results are revealed after voting, not before**, even on a live poll — a running tally shown to someone who has not answered is the bandwagon effect, and it makes the answer worth less than not asking. A live poll still offers "See results" to anyone who would rather look than vote, because refusing that would be pretending the tally is secret when it is not.
- The live refresh is a **5s poll, not Supabase Realtime**. Realtime applies row-level security to what it broadcasts, and the votes table permits a client to select exactly one row — its own — so there is nothing Realtime is allowed to send. It stops when the tab is hidden.
- A poll is created through `admin_create_announcement`, an RPC, because the announcement and its options must land in one transaction; through PostgREST that is two requests, and the gap between them is a published poll with no options on everyone's Today page. All six types go through it so there is one creation path, with the INSERT policy left as the backstop.
- The video embed is a **facade**: one thumbnail image, and the player mounted only on the tap that means "play" (with `autoplay=1`, so that tap is not spent). The modal auto-opens for every user the moment a video goes out, and a YouTube iframe is roughly a megabyte plus third-party cookies before anybody has decided to watch. The embed is `youtube-nocookie.com` for the same reason.
- `admin_list_announcements` is **dropped before it is created**, not `create or replace`: its `RETURNS TABLE` gained columns when polls and video arrived, and Postgres refuses to replace a function whose return type changed. It also lives at the end of `admin.sql` because it reads tables defined in §9.
- **Feedback is a form that feels like a chat, and the difference is deliberate.** No typing indicator, no agent avatar, and above all no model answering on behalf of a person. Four categories in one table — abuse included, because they differ in what the form asks and how urgently a human reads them, not in their shape, and a separate `abuse_reports` table would need its own policies and its own chance to get one of them wrong.
- `reported_name` is free text and is deliberately **not** a foreign key to a user: resolving one would mean shipping a user-directory lookup, which is the single thing a report form must not have. Reports are readable by their author and by administrators, and by nobody else — which is what makes the category honest.
- The insert policy pins `auth.uid() = user_id` **and** `status = 'open' and admin_response is null`; without the last two a user could file a ticket that arrived pre-resolved (so nobody read it) or carrying a forged reply from support. Users cannot update their own tickets: an editable message is a message that can be swapped out from under a decision.
- Admin replies are one-directional and not a thread. The submitter reads the reply under their own ticket and cannot answer it; a second message from them is a second ticket. That keeps the feature one table, and the inbox shows an email address for anything that needs a real conversation.
- **An unseen reply puts a red dot on the launcher** (`.fb-dot`, a sibling of the glass because the glass clips its children). Tapping it opens straight onto Your messages, where the reply is tagged "New reply". "Seen" is `feedback_tickets.reply_seen_at` (`admin.sql` §6b), kept on the server so reading on the phone clears the laptop. Unseen = a reply and `reply_seen_at` null or older than `responded_at`, so an edited reply lights the dot again. Students still have no UPDATE policy: `ack_feedback_replies(ids)` (definer, own rows, this column only) moves it, to `greatest(now(), responded_at)` because `responded_at` comes from the admin's clock. Acked when the list holding the reply is on screen. Checked on mount and on return to the foreground, throttled to two minutes, no polling or Realtime. `listUnseenReplies` never throws: before §6b is run the select fails and there is simply no dot. Tested in PGlite (10 checks).
- `feedback/api.ts`'s `humanError` is the only thing that reaches a user-facing surface — Postgres' own wording is at best unhelpful and at worst tells somebody exactly which wall they hit. Its `PGRST202`/`PGRST205` cases were checked against a live project, not guessed: PostgREST says "Could not find … in the schema cache", which no `does not exist` test would catch.
- The launcher is **bottom-left** (`.fb-dock` in `index.css`), a liquid glass circle, because the settings gear (`settings/QuickSettings.tsx`) owns bottom-right and two floating circles in one corner is how a product ends up with a thumb that can reach neither. Its geometry is CSS rather than Tailwind for the reason the plan grid gives, plus one it does not need: the dock has to clear the fixed rail on desktop and sit in the corner on a phone, which is a media query. `--rail` is set inline from the sidebar's own collapsed state.
- Nothing in either feature touches `AppState`, so nothing here ever fires a Supabase upsert of the whole blob — the same property `share/` has.

### Analytics (`analytics/`, `supabase/analytics.sql`)

- **Console → Analytics**, the console's first and default section (`analytics/AnalyticsAdmin.tsx`, lazy, ~12 kB gz). DAU/WAU/MAU, stickiness, accounts, sign-ups, hours studied (timed vs typed), week-by-week growth (stayed / new / came back / went quiet), day-1/7/30 retention and weekly cohorts, how many of 30 days people show up, the sign-up → habit funnel, streaks, exam/class/device/install/timer/theme splits, feature adoption, and Groups/Race/Decks/inbox figures. Range is 30d/90d/6m/1y, kept per device in localStorage.
- **Nothing on the server could say who used the app on a day before this**, which is why it needed a new table: `user_profiles.updated_at` is only the last write, `last_sign_in_at` doesn't move when an existing session opens the app, and `study_days`/`leaderboard_entries` exist only for opt-in features. `activity_days` is one row per user per 04:00-IST study day; the primary key is the dedupe. **Active on day D = a row for D.**
- **Neither table (`activity_days`, `usage_snapshots`) has a client policy, and both have grants revoked** — not even an admin can select them. Written only by `track_activity(p jsonb)` (definer, `auth.uid()`, server-computed day); read only by `admin_analytics(p_days)`, which returns counts and sums, and by `admin_recent_users(p_limit, p_before)` (§6b). One jsonb argument so adding a field never changes the signature (no PostgREST overload trouble).
- **Latest sign-ups (`analytics/RecentUsers.tsx`) is the one console reader that names people**, asked for on purpose so staff can see who just arrived. `admin_recent_users` (definer, `is_admin()` first) returns the newest `auth.users` with their public profile (name, handle, bio, avatar), exam/class/goal/streak from `usage_snapshots`, and days active, hours, last day, device and installed from `activity_days`. **Never an email, the synced blob or any study content** — widening it changes `site/legal.tsx` ("How the app is used") in the same commit. Keyset-paged on `created_at`, 25 a page, max 100. It loads separately from the dashboard, so a project that has not re-run `analytics.sql` keeps its charts and the card says to re-run it. Tested in PGlite (scratchpad): student and anon refused, paging, clamp, idempotent re-run.
- **The client sends numbers, never content** (`analytics/track.ts`): today's and yesterday's hours/timed hours/session count, platform, installed-PWA flag, and on a visit a dozen usage counts/flags (`usageFacts`). The server accepts totals only for today and yesterday, and yesterday only onto an existing row — logging hours never invents a visit.
- `useActivityPing` is mounted at App root (a visit happens on whatever tab opens), waits for `syncSettled`, never writes AppState. Triggers: arriving (a **visit** = load, or back after a 30-min gap or past 04:00, tracked per user in `analytics_visit_v1:<uid>`), today's logs changing (4s debounce), the tab hiding (flushes a pending change). A data ping whose totals were already sent is dropped, which also keeps StrictMode to one ping per load. Gives up for the session if the RPC is missing. Wiped on sign-out (`forgetAnalyticsOnDevice`).
- **History is reconstructed once** by `analytics_backfill()` (run at the bottom of the file, not callable by clients): study-log days with their hours, sign-up day for accounts that synced, last sign-in, Race days, deck reviews, group and Race chat. Those rows have `opens = 0`; a live ping promotes them. Days before the account existed are dropped (local-first logs can predate sign-up). The console marks where live tracking began and says earlier days are a floor.
- Rolling WAU/MAU are computed in one pass, not a distinct count per day: each active day covers the next 7/30 days up to that user's next active day, so a user's windows never overlap, and a +1/−1 running sum gives every day at once. Every optional-feature read in `admin_analytics` is guarded by `to_regclass` and its own exception block.
- Tested in PGlite (scratchpad): privileges for student/admin/anon, garbage payloads, clamps, the backfill, and every aggregate against a naive JS recomputation on random data — 102 checks, plus six planted bugs that each make the suite fail. `admin_analytics(365)` over ~128k rows ran in ~0.4s even in WASM Postgres.
- Charts are hand-drawn SVG (`analytics/charts.tsx`): line (crosshair), stacked/diverging columns, bars, split bars, cohort heat grid. Every chart answers hover and arrow keys and has a **Table** twin. Colours were run through the dataviz validator against `#ffffff`/`#111114`; `#E10600` is in none of them. Cohort cell text is picked by computed contrast; weeks still running are pale and outlined.
- `?analytics=debug` (DEV only) is the design board: busy project, brand-new project, not set up, failing, slow — plus a **ping inspector** that runs the real hook under StrictMode with a recorder instead of the network, showing every payload the app would send.
- Run `admin.sql` before `analytics.sql`, then deploy. The console shows a "not switched on" screen until the SQL is run, and the ping silently does nothing.

### Moderation (`moderation/`, `supabase/moderation.sql`)

- **Two removers, one notice.** A group's owner/admins remove from their own group (`remove_member`, which gained an optional `p_reason`); app staff remove from **any group, private included** (`staff_remove_group_member`) and from the Ranks race (`staff_remove_from_leaderboard`). Private groups used to be out of staff's reach; that left a student harassed in one with only its own admins to turn to. Staff still cannot *read* a private group — the `staff_*` functions return names, icons, roles and counts, never chat, hours or tasks — and `delete_group` stays public-only. Every removal writes a `moderation_notices` row; the reason is optional, the notice is not. A notice **never names the remover** — "an admin of X" or "Tracker Alpha".
- **Console → Moderation → Find someone** (`moderation/StaffFinder.tsx`) reaches anybody anywhere. People search reads `profiles` directly and opens `PersonPanel`: the race plus every group they're in (`staff_user_groups`), each with its own Hide and Remove, plus **Hide everywhere** (race hide + every-group hide). Group search (`staff_search_groups`, private included) opens `StaffGroupMembers`, the same roster the public Explore sheet shows staff.
- `remove_member` writes the notice through `EXECUTE` guarded by `to_regprocedure`, so `groups.sql` still installs without `moderation.sql`. Its signature changed, so the 3-arg version is dropped first. Run order: `groups.sql`, then `moderation.sql`, then deploy. The client leaves `p_reason` out when blank, so removal works against an unmigrated database.
- Notices are written only by definer functions (`record_moderation_notice` is revoked from every client role), readable only by their addressee — staff included — and marked read via `ack_moderation_notice`, never an UPDATE policy, so the reason cannot be edited.
- `useModerationNotices` is mounted at App root: fetch on session start (gated on `syncSettled`), Realtime INSERT on own rows, throttled re-check on tab return. Each new notice goes through `deliver` once (system notification if hidden) and fires its side effect **on arrival, not on "Got it"**: a race removal turns `leaderboard.enabled` off, a group removal re-reads the list. `RemovalNoticeModal` shows on any tab, never over a running session, and only "Got it" dismisses it.
- **A leaderboard removal is a server-side block, not a row delete** — the client republishes within a minute. `leaderboard_blocks` + restrictive INSERT/UPDATE policies refuse publishing. A plain removal is cleared by `rejoin_leaderboard()` (called by `joinLeaderboard` before enabling); a ban (`banned = true`) is refused there, also blocks race chat, and is lifted only from the console. A later plain removal never downgrades a ban.
- **Hide is the silent, timed tool** (`leaderboard_hides`, staff only). No notice, and the hide table is unreadable by the hidden person. Restrictive SELECT policies on `leaderboard_entries` and `race_chat_messages` (`leaderboard_row_visible`) drop the person's rows **from `from_date` on** for everyone but themselves until `hidden_until`, so they keep publishing and see their own place and chat as normal. Always timed (max 30 days, enforced by CHECK); "until next rollover" is `nextRollover()` = next 04:00 IST. It lapses by itself. Earlier days stay visible so profile totals don't visibly drop. Staff read the board through the same policy, so a hidden racer appears under "Hidden", not in "Today's race".
- **Group hides** are the same silent, timed tool inside groups. `group_hides` lives in **`groups.sql`**, not `moderation.sql`, because every group read must respect it and `groups.sql` must still install alone; only the staff writers (`staff_hide_in_groups`/`staff_unhide_in_groups`/`staff_group_hides`) are in `moderation.sql`. `group_id` null hides the person in **every** group, including ones joined while it runs (else a hidden person walks into a new public group and is heard). `group_row_visible(group, user, day)` drives a restrictive SELECT policy on `group_messages` and `group_message_reactions` (day = `ist_study_day(created_at/updated_at)`), and `group_leaderboard`, `group_task_progress` and `my_groups`' unread/last-message all filter by it. From `from_date` on, the hidden person's messages, reactions, hours and tasks vanish for everyone but themselves; earlier days stay. They **stay on the roster**, because dropping them would be a membership change with no notice, and the member count would disagree with the list. `group_hidden_from` answers null to non-members, so nobody outside a group can probe who is hidden in it. The roster returns `hidden_until` (this group) and `hidden_everywhere_until` separately: its Unhide lifts only this group's hide, and the every-group one is lifted from the console.
- Restrictive policies are used (and named separately) so re-running `leaderboard.sql`/`race_chat.sql`/`groups.sql` cannot drop them. Tested in PGlite (77 race scenarios, plus 57 for group reach and hides, including the upgrade from the previously deployed files).

### Chat bubbles (`chat/`) and race chat replies

- **One bubble for both chats.** `chat/ChatMessage.tsx` is used by group chat and race chat; the caller draws what is inside the bubble and the name above it, the shell owns every gesture: **swipe right** (touch) to reply, the bubble following 1:1 to the trigger then resisting, with a haptic tick; **long press** (420 ms, touch) or right click / Enter opens `MessageMenu` — the page dims, a DOM copy of the bubble is lifted (sliding to where the menu fits, as WhatsApp does), the six emoji above and Reply · Copy · Delete below; **double tap** is ❤️ with a heart bloom (it only adds, never takes back); with a mouse, **↩ 😊 ⋯ sit beside the bubble on hover** (Instagram web), 😊 opening the emoji bar and ⋯ Copy/Delete. One tap does nothing, as in WhatsApp. Delete is two-step inside the menu, not `window.confirm`. The menu is a portal, measured once on open, and closes on any scroll or resize rather than drifting.
- A gesture never re-renders React: the swipe writes `transform` to the bubble and arrow, the press state is `data-pressing`. The hover strip is hidden under `(hover: none)` in `chat/chat.css` (a tap leaves `:hover` stuck on touch screens), and bubbles drop the iOS callout and text selection there so a long press opens our menu; Copy covers copying.
- `chat/reactions.ts` holds the emoji set (mirrored by CHECKs in `groups.sql` and `race_chat.sql`), `mergeReactions`, `stamp` and `groupReactions`; `chat/QuoteBlock.tsx` the quote. `?chat=debug` (DEV) is a fixture thread for trying the gestures with no database.
- **Race chat now has replies, reactions and deletion** (`supabase/race_chat.sql`, second half, re-runnable), shaped exactly like group chat's: `reply_to` (same race only, checked by an insert trigger that also forces `deleted_at`/`deleted_by` null), `race_chat_reactions` (null-emoji take-back, `race_date` copied by the RPC for the realtime filter), `react_to_race_message` (refused to banned racers) and `delete_race_message` (soft delete; own message, or anyone's for `is_admin()`, so `RanksTab` takes `isStaff`). Deleted messages now show as "Message deleted" instead of vanishing. A hidden racer's reactions are hidden like their messages (policy in both `moderation.sql` and `race_chat.sql`, whichever runs last). Until the SQL is re-run, `leaderboard/chatApi.ts` falls back to plain chat with the extras hidden. `useRaceChat` now also listens for UPDATEs and re-fetches on every rejoin and on return after a minute away.

### Groups (`groups/`, `supabase/groups.sql`)

- The **Groups** tab: create a group, invite by link or code, a leaderboard (today/week/month/all time), a persistent chat, and opt-in task sharing. Server state end to end — **nothing about a group lives in `AppState`**, so no group action ever fires `triggerSync`. `GroupsTab.tsx` is a zero-logic container like `schedule/PlanTab.tsx`; `useGroups` is mounted at App root beside `useRace` because what a group sees of you must stay current while you're on Today.
- **Almost nothing is directly writable.** Groups, memberships, roles, invites and bans have **no INSERT/UPDATE/DELETE policies** and change only through definer RPCs that check the caller's role as their first statement (`user_roles`' stance in `admin.sql`). An UPDATE policy on `group_members` could not stop the same request setting `role`. The two direct writes are the ones whose rule really is "your own row": posting a message and publishing your own study data. `is_group_member()`/`group_role()` are the only predicates, and are `security definer` for `is_admin()`'s recursion reason.
- **Ownership lives only on `group_members.role`** (one-owner partial unique index), never a `groups.owner_id` — two places saying who owns a group can disagree. One AFTER DELETE trigger handles succession for every way a row disappears (leave, removal, account-deletion cascade): longest-standing admin, else member; **an emptied group is deleted** so an old link cannot let a stranger walk into its history alone. The trigger stands aside when the group itself is being deleted.
- **Study hours come from `study_days`, not `user_profiles`.** One row per user per study day (`hours` + `tracked_hours`), published by `groups/publish.ts` as a diff against a per-user localStorage ledger, and fully once per session as a self-heal. It is a *projection*, not per-group and not a copy of sessions: every group reads the same row. Reading the jsonb blob from a definer function was rejected for `reminders.sql`'s reason — one bug in its membership check leaks everyone's whole private life. `leaderboard_entries` was rejected because it is readable by every signed-in user; writing rows there for somebody who only joined a friends' group would publish their hours app-wide. Leaving your last group deletes your rows (`withdrawAll`). **Ranks on `tracked_hours`** — the Race's rule, and the board's footnote says so.
- **Privacy is per membership, default nothing.** `share_hours` (DB default false; the join screen shows it pre-ticked, visibly) and `share_tasks` `private | summary | tasks`. `task_shares` holds today's snapshot at the **widest** level any group is allowed; `group_task_progress()` cuts it down per group, so "tasks with friends, a count with the coaching batch" is enforced by the database, not the screen. `group_leaderboard()` still lists members who hide hours (with nulls) — dropping them lies about who is in the group, ranking them at zero lies about them — and always shows callers their own figure. Both switches are one component (`groups/SharingFields.tsx`) asked in all three places — create, join, and the group's **settings sheet** (`GroupSettingsSheet.tsx`, opened from the header's gear or from the sharing sentence under the group's name) — and the group header always states what you share, one tap from changing it; task sharing used to exist only a screen deeper than hours, and users concluded it did not exist. Create/join set the task level with a follow-up `set_group_sharing` call rather than a new RPC parameter, so no migration re-run is needed; if it fails the level stays `private`, the safe side. **The sharing copy is the feature, and it was rewritten after users could not follow it** ("Today's tasks: Private / Count / Full list" left them asking which tasks, whose, and what "full" meant). Every string now names the thing by what students already call it — **Focus Tasks, on the Today tab** — says who sees it (other members of this group), and gives a concrete example; the three levels are **Hidden / Just a count / Every task** (`TASK_LEVEL_LABEL`/`TASK_LEVEL_COPY` in `SharingFields.tsx`, the only source). Under the controls is a **literal preview** — your own row drawn by the same `PersonRow` (`GroupPeople.tsx`) the Members list draws everyone with, from `taskSnapshot` (the function that publishes) — so "what do they see" is answered by showing it and cannot drift from what leaves the device. Keep new copy concrete; no abstract nouns.
- **Invites**: 12 chars of Crockford base32 = 60 bits from `gen_random_uuid()` (CSPRNG; not pgcrypto, per `profiles.sql`). Stored in the clear so an admin can re-copy a link; readable only by the group's admins and the invite's creator. `preview_invite`/`redeem_invite` **return a status instead of raising**, because a raise would roll back the brute-force throttle's failure count (15 wrong codes per 15 min). Redeem locks the invite row `FOR UPDATE` so two people cannot both take the last use; already-a-member succeeds without spending one. Remove and ban are different decisions (`group_bans`). Members may invite only under `invite_policy = 'members'`, max 3 live links, each ≤ 7 days.
- Invite links are **`/?join=CODE`, not `/join/:code`** — no router and no server rewrite; the root is the one URL guaranteed to serve the app. `groups/invite.ts` lifts the code into localStorage on first render and strips the URL, because the recipient is usually a first-time visitor who still has sign-up, email confirmation (a new tab) and onboarding ahead. A pending invite **skips the landing page**, routes to Groups once visible and again after sign-in, and outranks the last-opened group.
- **Public groups and Explore.** `visibility` (`private` | `discoverable`) says who can *find* a group; `join_policy` (`invite` | `open` | `request`) says how a finder gets *in*. A biconditional CHECK ties them — private ⇔ invite — so a private group can never carry a stale `open` that `join_public_group()` would honour, and a listed group can never be a dead end; `normalize_group_access()` is the one place a pair is decided. **Access is the owner's alone** (`update_group` refuses a changed pair from an admin): going public puts a name in front of every student. Listing exposes name, icon, description and member count — nothing a membership would reveal; hours, tasks, the roster and chat stay members-only by the same functions that already refused non-members. `explore_groups()` escapes `%`/`_` in the search and caps a page at 50. Requests (`group_join_requests`) carry the requester's **own sharing choices**, so approval applies what they agreed to rather than a default; `respond_join_request()` re-checks bans and limits at approval time, and going private drops pending requests. 10 pending requests per person. Invite links work regardless of `join_policy` — an admin's own say-so. App staff can take down a **public** group (`delete_group` calls `is_admin()` through `EXECUTE` guarded by `to_regprocedure`, so the file still installs without `admin.sql`); private groups are not theirs to see. `create_group`/`update_group`/`my_groups` are **dropped before being recreated** — a changed argument list would otherwise leave an overload that makes PostgREST calls ambiguous, and a changed return type cannot be `create or replace`d — and the new arguments default, so run the SQL first and deploy after; both clients work in between.
- **Chat: Postgres is the mailbox, Realtime is the doorbell.** Scale was estimated before choosing it — 10k users/1k groups/20 msgs a day is 7.3M rows/year (~2GB with index), every read an index range scan on `(group_id, id)` whose cost is independent of table size. A second service would add auth, RLS and backups to duplicate for no concrete gain; blob storage cannot do per-message moderation or realtime. Retention SQL is commented at the bottom of the migration, not run.
- `group_messages.id` is a **bigint identity**: a total order two messages in the same millisecond cannot tie on, and the pagination cursor by itself (`id < oldest`). `client_id` (uuid, unique per sender) makes a send **idempotent**: a retry after a lost response hits 23505 and fetches the row that already landed, and the realtime echo is matched to its optimistic bubble by that id. The insert trigger owns `created_at`/`deleted_at` and a flood guard (15 per 30s). Deletion is `delete_group_message()` — a **soft delete that blanks the body**, so open clients get an UPDATE and nobody holds text the server has forgotten.
- **Realtime authorization is the SELECT policy.** Postgres Changes evaluates RLS per subscriber, so a non-member subscribing with `group_id=eq.X` receives nothing whatever the client does. No Presence: a public channel topic is joinable by anyone who guesses it.
- `useGroupChat` **opens the channel first and fetches the latest page on every `SUBSCRIBED`** (first and every rejoin), merging everything by id — order-independent and idempotent, so the fetch/subscribe gap cannot lose or double a message. Catch-up is "fetch the latest page again": it either overlaps and merges, or (a long outage in a busy group) **resets the window** with `hasOlder` set so the gap is reachable by scrolling, never silently glued over. Also on `online`, tab return and a 60s safety poll. Deletion wins every merge; an older-page request carries the window's generation and is dropped if the window was reset under it. Unsent messages persist per **user and group** (a shared laptop's next account must never retry the last one's words) and are wiped on sign-out (`forgetGroupsOnDevice`).
- **Replies and reactions** (gestures are the shared bubble's, see Chat bubbles below; tap a quote to jump to the original). A reply stores only `reply_to` — the quote is never copied, so deleting the original blanks every quote of it; the insert trigger refuses a parent from another group. Quotes are read from the window or looked up by id (`fetchQuotes`), deliberately not a self-referencing PostgREST embed. Reactions are `group_message_reactions`, **one per person per message** (the PK is the dedupe), a fixed six-emoji set enforced by CHECK (free text would be a second, unguarded message channel), written only by `react_to_group_message()`. **Taking a reaction back sets `emoji` to null; the row is never deleted while its message exists** — Realtime can neither filter DELETEs nor apply RLS to them, so a delete would broadcast to every subscriber in every group. The client merges by server `updated_at` (parsed, not string-compared) and draws in-flight changes from a separate `pending` overlay so a server timestamp is never compared with the device clock. Until `groups.sql` is re-run, `chatApi.ts` detects the missing column/table once and falls back to plain chat with replies and reactions hidden.
- Chat scroll: "stick to bottom" is cleared **only by the reader scrolling up**, never inferred from geometry at scroll-event time — a font swap between our own scroll-to-bottom and the event it queues made a reader look 737px away who never moved. A per-render layout effect plus a ResizeObserver re-pin while stuck.
- **Layout rule: one row of tabs per screen, content before controls.** It was rewritten after users found it cluttered — two tab bars stacked on the Board (sections, then Today/Week/Month/All time), and the Members tab opening on an invite builder with two more rows of options above the roster. Now: the list has one "New group" button, the My groups / Explore switch, and "Join with code" as a line under the list (the empty state carries both actions itself). A group has **Board · Chat · Members** only — the old Tasks tab merged into Members, where each person's Focus Tasks for today sit on their own row (`GroupPeople.tsx`). The period is a light filter inside the leaderboard card, and the old stat cards are one summary line. Everything that is a setting rather than something to look at is a sheet opened from the header: **Invite** (`InviteSheet.tsx` — one "Create invite link" with a week/unlimited default; expiry and uses behind "Change") and the **gear** (`GroupSettingsSheet.tsx` — your sharing and its preview, then edit, bans, leave, delete). Don't add controls back onto the tabs.
- Styling follows the Ranks tab (`groups/ui.tsx` collects the tokens). Accent red is spent on the viewer's own row, unread badges and actions; other members' bars are neutral.
- Tested against the real SQL in PGlite with a Supabase-shaped `auth` schema, roles and default privileges (146 RLS/RPC scenarios including the upgrade from the previously deployed file, and planted policy holes to prove the suite fails). Supabase grants function EXECUTE to `anon` by name, so every function is revoked from `public, anon`, not just `public`.

### Account deletion and the legal pages (`account/`, `supabase/account.sql`, `site/legal.tsx`)

- **Review → Account & sync → Delete account** (signed in only) opens `account/DeleteAccountSheet.tsx`: what goes, a typed `DELETE` (case-insensitive, phones capitalise unpredictably), and no dismissing mid-flight. Google Play requires in-app deletion for any app with sign-up.
- **Two halves, files first** (`account/deleteAccount.ts`). Storage objects cannot be deleted from SQL, and each bucket's delete policy checks a row the database half removes (a personal deck for `decks`, the `cbt` feature for `qbank`), so avatars, CBT figures and personal-deck images go while those policies still say yes. A failure there stops before the irreversible step. Then one RPC, `delete_my_account()`.
- **`delete_my_account()` exists for the three things that do not cascade from `auth.users`**: the last administrator is refused (same rule as `revoke_admin`); `race_chat_messages.deleted_by` has no ON DELETE rule, so anyone who ever deleted a race message could not be deleted until it is nulled; and `user_profiles` was made in the dashboard, so its foreign key is not trusted and the row is deleted by hand. Personal decks need nothing here: decks.sql §6 deletes a personal deck when its owner is nulled. Everything else cascades, and group ownership passes on by the succession trigger.
- **The avatars bucket had no SELECT policy**, so `list()` returned nothing and `remove()` (a DELETE that Postgres also filters through SELECT policies) removed nothing. That made avatars undeletable, and `uploadAvatar`'s "remove the old one" never ran, so every replaced avatar is still in the bucket. `account.sql` adds an own-folder SELECT policy. Public URLs never consulted RLS, so nothing visible changed.
- On success App holds sync off for good (`preventSyncOnUpdate`), signs out locally, runs `forgetAccountOnDevice()` (shared with sign-out so the two cannot drift), and resets state to the default before reloading. Signing out changes `user?.id`, which re-runs the effect that writes `locked_in_state_v2`, and it must write the default, not the deleted account.
- Tested in PGlite against every SQL file (22 checks: permissions, last admin, a scan of all 94 uuid columns for the deleted id, group succession, Alpha decks surviving an admin, avatar storage), plus planted holes for each safeguard. Run `account.sql` any time; it guards every optional table with `to_regclass` and re-runs cleanly.
- **`/privacy/` and `/delete-account/`** are built with the guide pages, in the same shell, but are not guides: no FAQ markup, not in the guide lists or llms.txt, only in the sitemap and the footers (guides, landing, Review's "Talk to us" row). `/delete-account/` is the URL Play asks for: steps, an email route for anyone who cannot sign in (a parent included), and what is kept. Its button is `/?open=review#account` (`review` is a deep-link tab; ReviewTab scrolls to `#account`).
- **The privacy policy describes what the code does today, sentence by sentence.** A feature that starts collecting something new changes `site/legal.tsx` in the same commit and moves `POLICY_EFFECTIVE`. It is not legal advice, and it does not implement verifiable parental consent for under-18s, which India's DPDP Act requires.

### Timer

`TimerState` is a stopwatch per subject, stamped with `blockId`/`chapter` only when the session was started from a Plan block. Ending logs the session at once as `source: 'timer'`, with the 1–5 focus quality picked on the card and its `startedAt`/`endedAt`. Pomodoro is the other mode (see below). "Wipe" on a history row deletes that logged session.

- **The stopwatch pauses** (`today/stopwatch.ts`, pure). Three states from two fields: running has `startTime`; paused is not running with time banked in `accumulatedMs` and `pausedAt` marking where the clock stopped. **A pause logs nothing** — End logs the session once. Every "is a session in flight" check uses `isArmed` (running *or* paused), never `timer.isRunning`: the mode switch, the hidden-mid-session strips, Plan's Start now, `heldMode`, the reminder and removal-notice gates. `isRunning` alone is still right where it means "the clock is moving" (the race's `onTheClock`).
- `sessionSpan` places a session on the clock as one contiguous stretch of exactly the time served, **ending where the clock last ran** — the pause, for a session ended while paused. A pause inside a session is never counted as study by the analysis, which reads `endedAt - startedAt` as a duration. Same convention as a Pomodoro block cut by a pause.
- `logStudy` dates a measured log by its `endedAt`, not by today: a session ended this morning from a pause last night belongs to last night. **Resuming a pause that crossed the 04:00 rollover banks the earlier time first** (`resumeRun`), as its own log on its own day with its Plan block, and starts a fresh run that keeps the chapter but not the block — otherwise last night's minutes would move onto today and off the streak.

**Lock-In mode no longer exists** — no fullscreen, no "SESSION BREACHED" screen, no 15-minute minimum — and nothing counts distractions any more: the stopwatch and Pomodoro both log `distractions: 0`. `DailyLog.distractions` and the distraction term in `calculateLockInScore` only matter for older logs. The Lock-In *score* (Review tab) and the `LOCK IN` wordmark are separate and still exist. Do not describe Lock-In mode or distraction counting anywhere user-facing; the landing page once did.

### Pomodoro (`today/pomodoro.ts`, `today/usePomodoro.ts`, `today/PomodoroTimer.tsx`)

- **`usePomodoro` is the engine and it is mounted in `App.tsx`, not in the timer component.** A block has to keep running — and keep logging — while the user is on the Streak tab, or on no tab at all. When the loop lived inside `PomodoroTimer` it stopped existing the moment that component unmounted, and the bell never rang. `PomodoroTimer` is a view over the runtime plus the engine's controls; its own 250ms tick only redraws the clock.
- **Time served is never lost.** A block's `DailyLog` is written the instant the block ends — bell, `end()`, `reset()`, or switching to the stopwatch — at neutral quality 4, and rating it afterwards only amends that log (`pendingRating` holds `logId`, never unlogged hours). The old shape parked an unlogged block in `pendingBlock`, so stopping a 60-minute block after 15 minutes threw away the 15 minutes, and a second block finishing before the first was rated overwrote it. `pendingBlock` survives in `types.ts` only to be flushed once from old saved state.
- **Three runtime states, told apart by two fields** (`isIdle`/`isPaused` in `today/pomodoro.ts`): idle is `phaseTotalMs === null`; running has `phaseEndsAt` set; paused keeps `phaseTotalMs` with the time banked in `servedMs`. Everything is derived from the wall clock — `servedMs` is stale by design while running. `phaseTotalMs` is captured at start, so editing the block length mid-phase cannot change what the running block earns.
- Ending a work phase early logs whatever was served (floor `MIN_LOGGABLE_MS`, one minute) and advances to the break, but only fills a dot in the set if at least `COUNTS_TOWARDS_SET` (half) of the block was served — otherwise four ten-second blocks would buy a long break.
- A bell that rang while the tab was hidden is settled at `phaseEndsAt`, so the hours land on the study day they were served, and auto-start is suppressed (chaining off a bell nobody heard fabricates phases). Past `STALE_PHASE_MS` (12h) the phase is dropped instead of logged — the browser was closed, not studied through.
- Settling is idempotent: guarded per `phaseEndsAt` and by a 500ms floor between settles, because a timeout, a 5s safety interval, a visibility handler, and a double-tap can all reach for the same transition.
- The runtime is device-local — all three sync merge paths in `App.tsx` keep the local `pomodoro` — so `normalizePomodoro` (`state.ts`) only ever sanitizes this device's own localStorage, and `commitPomodoro` bumps `lastUpdated` only when a log is actually written.

### Sound (`audio.ts`, `sound/`, `film/scripts/render-sfx.ts`, `public/sounds/`)

- **Made offline, in `film/`, by the film's own DSP.** `film/scripts/render-sfx.ts` builds every cue from `film/scripts/audio/sfx-instruments.ts` (marimba, glockenspiel, bubble pop, soft thud, sparkle, tear) on top of `dsp.ts`, masters each to −1 dBFS, trims the tail at −54 dB, and encodes **ADTS `.aac`** with `afconvert` into `public/sounds/` (mono 48 kbps, stereo 80 kbps; 30 files, ~400 kB, core set ~150 kB). Run `npm run sfx:generate` (or `cd film && npm run sfx -- --only=streak`). Not `.m4a`: afconvert pads every MP4 with a ~3 kB `free` atom, a quarter of a tap's file. The style is **bright and playful, in D major**, chosen over the film's D-minor tines and engine; the parallel major keeps the two a family. Remotion has no synthesiser; its part is the **SoundBoard** composition (`film/src/sfx/SoundBoard.tsx`, data in the generated `board.generated.ts`), where every cue can be heard and judged in Studio. The WAV masters in `film/public/sfx/` are gitignored; the `.aac` files are committed.
- **`sound/cues.ts` is the one list of ids**, read by the renderer (which refuses to run if an id has no recipe) and the player. `gain` there is the only loudness control: masters all peak at the same level, so a level change is a one-line edit, tuned at `?sfx=debug` (DEV only), which plays each cue through the real chain.
- **The player is Web Audio, not `<audio>`.** A desktop student rates cards with 1–4 faster than an element can rewind; combos need `playbackRate`; and once a context is unlocked it plays for the rest of the session without another gesture, which the pack opening and the Pomodoro bell need. The context is created on the first `pointerdown`/`keydown` (never before: Chrome warns), and a `play()` that arrives while that first resume is in flight waits for it, decoding in parallel (`UNLOCK_LATE_MS`). A decode-time trim skips AAC's encoder delay (42 ms mono / 65 ms stereo) but is capped at 70 ms, because a cue that opens on a quiet riser has real sound under any threshold.
- **Loading:** the `core` group's bytes are fetched on idle once the app is on screen (`prefetchCore`, called from App when `showLanding === false`) — never under the landing page. `store` loads when the store opens, `rare` when `UnlockModal` mounts. A cue still loading plays only if it arrives within its `late` budget; a "correct" half a second late is worse than none.
- **Rules:** sound is **on unless this device said off** (`lockin_sound_enabled === 'false'`; the onboarding gate's "Continue silently" and the mute button write it). Preferences are device-local, never `AppState`. A hidden tab plays nothing except `background` cues (the two Pomodoro bells). Never call `sfx` inside a `setState` updater (StrictMode runs those twice); work out what changed from `stateRef.current` first, as `celebrateLog`, `toggleChapterStatus` and `soundForTaskMove` (`sound/moments.ts`) do. **The CBT exam is silent on purpose** (NTA conditions), and so is group chat. The toast bus makes no sound: the bell would then ring twice.
- **The Pomodoro bell rings on the audio clock.** Desktop Chrome slows timers in a tab hidden for five minutes to once a minute, so a bell left to the watchers could be a minute late. `usePomodoro` schedules the bell with `scheduleAt` the moment a phase starts; pause, end and reset withdraw it; `bell()` calls `claimScheduled` and rings only if the scheduled one never started (a laptop that slept). The block's log carries `rang` so `celebrateLog` does not stack a "logged" sound on the bell.
- **Variable reward is tied to real effort**: logged sessions sound bigger by length (`loggedCue`), task completions climb D major pentatonic per task done today (`comboSemitones`), the last open card is a flourish, right answers in a row climb in chapter tests, error tests and the review room (Again resets, Hard only ticks, Easy jumps two steps), and a clean sweep gets `target-hit`.
- **`M` mutes from anywhere** (`useSoundHotkey`), ignored while typing or with a modifier. The header has a 🔊/🔇 button; Review → Settings has the switch and a volume slider (squared to sound linear) that plays a sample on release.
- **Testing in the browser pane:** the pane reports `document.hidden === true` when it is not on screen, so every visibility-gated sound looks broken there. Shim `document.hidden` to false in the page, then hook `AudioBufferSourceNode.prototype.start` to record what fires.

### Firewood: streak extenders (`streak/firewood.ts`, `streak/FirewoodCard.tsx`)

- A missed day burns one **firewood** instead of ending the streak, and the streak **holds** at its number: firewood never adds a day. Each Monday-to-Sunday IST week with at least one study day earns **3**, credited on that week's first study day; unused firewood banks with no cap. A week with no study earns nothing, so a bank of 30 is really 30 days away. Today never burns (it is not over). An empty bank on a missed day ends the streak as before.
- **It starts on a fixed launch day, `FIREWOOD_SINCE` (`2026-10-15`).** Before it the old rule applies (a missed day ends the streak, nothing is earned or burned), so streaks, longest runs and rewards from before launch are exactly what the old code computed: no backdated holds, no surprise unlocks, no inherited banks. The bank starts at 0 and fills from each student's first study day of a launch-or-later week. Never move the date and never make it "today". `ledgerFromDates` takes it as an optional third argument so tests can exercise the mechanics.
- **Derived, never stored.** `ledgerFromDates` replays the log history day by day; `streakLedger(logs, { verified?, today? })` in `utils.ts` wraps it with a WeakMap cache (App reads the streak on every render, ten a second mid-session). `calculateStreak`, `calculateVerifiedStreak`, `longestStreak` and `longestVerifiedStreak` all read the ledger, so the Streak tab, rewards, share cards and analytics agree without knowing about firewood. **The timed (verified) streak gets no firewood** (`NO_FIREWOOD` as `since`): the book and hamper cost real money, so they need an unbroken run of timed days and a missed day always ends it. Because it is derived it syncs for free and cannot be edited into existence; a backfilled day turns a burn back into a study day.
- `holding` means held right now: yesterday was burned and today has no log yet. The Streak tab says so in its subtitle and the card; the streak moment says "Firewood held it for N days", shows burned days amber in the week, and the bank. Firewood is amber (`#F59F00`), never the accent red.
- `streak/firewood.ts` must not import `utils.ts` (utils imports it). Name clash: the UI is `FirewoodCard.tsx`, because macOS resolves `./Firewood` to `firewood.ts`. Tests: `npm run test:streak` (`streak/tests/`, run by `scripts/test-decks.mjs <folder>`).

### The streak moment (`streak/StreakMoment.tsx`)

- **Liquid glass** (`LiquidGlass`, `lg-pop`) over an unblurred sibling scrim. Duolingo's stickiest screen, in this app's voice: once a day, the first time a session is logged **on this device**, the app stops and shows the streak rolling from yesterday's number to today's, the last seven days, one short line (deterministic on the number), and the days to the next reward. The sound is the tier cue (`streakCue`: 1–6, 7–29, 30–99, 100+, plus milestones 7/30/50/100/200/365).
- **Only a log written here, for today, opens it** — `celebrateLog` is called from `logStudy` and `commitPomodoro` only, so sync, realtime and past-date backfills cannot. Once per study day per device (`streak_moment_v1:<uid|local>`). A moment that opens in a hidden tab (a background Pomodoro bell) waits to be seen before it makes a sound.
- **Order:** it goes before `UnlockModal`, so on day 30 the streak lands first and the reward follows when it is closed; announcements, removal notices, the install banner and the feedback launcher all wait behind it.

## Product philosophy & tone

The product frames studying as high-stakes competition, not a gentle habit tracker — copy is deliberately blunt, uppercase, and pressure-inducing ("THE COMPETITION IS STUDYING. ARE YOU?", "YOUR COMPETITION IS LOGGING HOURS RIGHT NOW.", "Now stop reading and start studying."). Actions are phrased as commitments/consequences (`ENGAGE` / `ABORT`, `WIPE`, `SESSION BREACHED`, `LOCK-OUT: 00:04:12`) rather than neutral CRUD labels. Preserve this voice in any new UI copy — avoid softening it into generic encouragement.

### Landing page (`LandingPage.tsx`, `landing/`, `scripts/prerenderLanding.ts`)

- **Editorial × Apple**: Satoshi 900 headlines against Playfair italic second lines (the red full stop is the brand mark), paper sections between dark ones, and the product shown as hand-built HTML/CSS vignettes (`landing/Vignettes.tsx`) in the app's real subject colours — no screenshots to go stale, no image downloads. The JEE/NEET toggle in the hero swaps the H1, both countdowns and the subjects shown.
- **All copy lives in `landing/content.ts`** and is read three times: by the page, by `landing/seo.ts` (JSON-LD `@graph`: Organization, WebSite, WebApplication, WebPage, FAQPage) and by `/llms.txt`. The FAQPage markup is therefore word-for-word the visible FAQ — Google ignores structured data that disagrees with the page. Rules in that file's header: short plain sentences (teen readers, see the copy memory), the phrases students search ("crack JEE 2027", "study tracker", "syllabus tracker", "Pomodoro timer"), FAQ answers that lead with the answer, and **no invented numbers, users or reviews** — every claim must be true of the app today. The old page's testimonial and "hundreds of students" claim were dropped for that reason.
- **Pre-render + hydrate.** The `prerender-landing` Vite plugin (runs in `closeBundle`, so both `vite build` and `npm run build` get it) bundles `landing/prerender.tsx` with esbuild, `renderToString`s the page, and writes it into `#root` with `data-lp-built=<build time>`, plus the JSON-LD and `dist/llms.txt`. It throws on any failure: a deploy without its landing HTML would silently drop out of search. `index.tsx` then `hydrateRoot`s when the visitor will see the page, else clears `#root` and `createRoot`s.
- **Hydration contract**: the first render must equal the build's. `landing/clock.ts` gives both sides the build time (`landingNow()`), and countdowns move to the real clock in an effect. No `window`/storage reads in render, no `useId`. Anything that moves on arrival is CSS; scroll reveals use native scroll-driven animations under `@supports (animation-timeline: view())`, so nothing is ever hidden waiting for a script and nothing touches React-managed class names.
- **Who sees it** is one predicate in three places that must agree: `landing/gate.ts` (`landingWillShow`), its hand copy in `index.html`'s inline head script (adds `html.lp-skip` before first paint so returning, signed-in and invited visitors never see a flash), and App's initial `showLanding` state (so a first-time visitor hydrates on the first render instead of seeing a blank screen while `getSession()` runs). Same rule as before: first-time, signed-out, no invite. `hasVisited` is still set by the CTA.
- Styles are hand-written in `landing/landing.css`, scoped under `.lp`, **not Tailwind**: the CDN runtime cannot style HTML before scripts run, and its preflight arriving later must change nothing on screen, so the stylesheet sets its own box model and margins.
- **Never write a literal `</head>` inside an `index.html` comment**: Vite injects the built CSS/JS before the first one it finds, which commented out the whole bundle once.
- Exam dates are not announced for 2027: the JEE countdown counts the days left in 2026 ("Session 1 is expected in January"), NEET counts to 2 May 2027 ("usually the first Sunday of May"). Update `EXAMS` in `content.ts` when NTA publishes the calendar.
- Verify with `npm run build && npx vite preview` (the `tracker-alpha-preview` launch config): the dev server has no pre-render.

Dark-first, with a light theme toggled via `state.theme`. One accent red (`#E10600`) for actions, progress and the now-line, and nowhere else. Fonts (see `index.css`; the display face is **Satoshi heavy**, not Anton):

- `font-ui` (Satoshi) — all body/labels/buttons/nav/inputs.
- `font-accent` (Playfair Display italic) — one short phrase per moment, never chrome.
- `num-timer` — the session/countdown timer.

**Native chrome, no web header.** There is no page header above the tabs any more (`Header.tsx` was deleted): the app reads as a native app, not a site. Its controls moved: notifications, sound, dark mode, the account (Google or guest) and Install live in **quick settings** (`settings/QuickSettings.tsx`), a liquid glass gear bottom-right that opens a liquid glass pane, with "All settings" leading to Review. **Class 11/12 is the class switch (`settings/ClassSwitch.tsx`) on the Syllabus tab only**, the tab it changes most: at the right end of the phone's capsule (other tabs keep a spacer there), and on a laptop its own glass pill in the corner (top in line with the rail, right in line with the gear), which is why `<main>` starts at `md:pt-16`. **On every other tab it is a row in quick settings** (`showClass`), so the corner is clear (Notes needs it to be a writing room). One tap switches, with no confirm: it is a view (progress is kept per class). What it changes is said in words — a note grows out of it on hover, keyboard focus or a tap of the word "Class", and after every switch ("Switched to Class 12 · Syllabus, Plan and Today now show Class 12 chapters. Your Class 11 progress is saved."), then folds back by itself; it is a portal that takes no pointer. Under 360px the word drops and the numbers stay. On a laptop the festive plaque hangs from under it. The exam countdown is a thin red calendar beside Today's title (`today/ExamCountdown.tsx`) that opens a glass pane. **Voice control was removed entirely** (`voice/`, its scripts and `public/voice`). **The Observatory tab was removed** (`analysis/`, `insight/`): a saved `lastUsedTab` of `Observatory` falls back to Today, and its data (`analysis`, `sleep`, `ai`) still rides AppState and every merge path untouched. Its `.obs` stylesheet stays because `notify/NoticeLine.tsx` borrows those tokens.

**`ui/kit.tsx` is the visual vocabulary of every tab.** It was first written for Mocks and then adopted app-wide, so a new screen should start from it rather than restating a ternary on `dark`. It provides `tokens(dark)`, `btn`, `PageHeader`, `Card`, `StatTile`, `Eyebrow`, `Chip`, `Segmented`, `Field`, `Switch`, `Sheet` and `Overlay`. The rules it encodes:
- **Every tab opens with `PageHeader`**: a display title, one muted line saying where things stand, and the tab's single control on the right. Mid-session Today hides it, because the clock is the page then. The landing page is exempt.
- **Cards** are `rounded-xl border`. Dark is `bg-[#111114] border-white/[0.06]`; light is `bg-white border-zinc-100 shadow-sm` on the page's paper (`#F2F0EC`, set in App/Sidebar only). Insets are `bg-zinc-50 border-zinc-100` / `bg-white/[0.025]`.
- **Light-mode ink is the zinc scale**, never the old warm hexes (`#E3E0D9`, `#8A8577`, `#17150F`, `#B5AFA0`…), which were migrated out of every tab component. They survive only in the app chrome and the landing page.
- **Labels** are eyebrows: 10px, bold, uppercase, `tracking-[0.06em]`, zinc-400/500. Headings are sentence case. No 8–9px `font-black` labels with wide tracking, except inside genuinely tight boxes (the timeline's "Moved" badge, the condensed phone task cards).
- **Selection is ink, not red.** A selected chip, day or segment is zinc-900/white. A data-coloured selection wears its own colour (a subject, an exam). Red is the primary button (`tokens().primary`, which carries a soft red glow) and progress.
- **Motion** is `mk-rise` with a small staggered `animationDelay`, plus `mk-fade`/`mk-draw`/`mk-grow-x`/`mk-ring`, all disabled under `prefers-reduced-motion`. **Never put `mk-rise` (a transform) on an ancestor of `fixed` UI.** It becomes the containing block: the task board deliberately has the card styling but no animation for this reason.
- **The navigation is liquid glass** (`ui/LiquidGlass.tsx`). It floats in the Apple manner: a capsule over the page on a phone (`.nav-capsule`, iOS 26's bars) and an inset panel on a laptop (`.nav-rail`, macOS Tahoe's sidebar). On a phone the menu hangs *below* the capsule so its close button is never covered. The rail's footprint is the panel plus 8px a side, **72 collapsed, 212 open**: App's `md:ml-[…]`, FeedbackWidget's `railPx` and the `--rail` fallback must agree.
- **Maps are built off the first frame**: drawn on CPU canvases (`willReadFrequently` — encoding a GPU canvas forced a readback that stalled the main thread ~400 ms behind a heavy paint), encoded with async `toBlob`, cached by size so identical tiles share one map, and scheduled on idle. Until a map lands the glass is frosted.
- The bending is real refraction of the live page: `backdrop-filter: url(#filter)` runs an SVG `feDisplacementMap` over whatever is behind. The map is drawn per element size from a rounded-rect distance field, with a convex squircle rim and the sideways shift from Snell's law (n = 1.5) written into R/G. B carries a frost mask, so the filter blurs the refracted image and lays it back over the middle only: **crisp bending at the rim, frosted body** so a label reads over a busy page. A CSS blur after the `url()` would soften the rim too, and Chromium rasterises that chain at CSS-pixel resolution, so it doubles on a 2× screen. A specular rim (light top-left, glint bottom-right) is drawn from the same field at device resolution.
- **`chroma` (0–1, off by default) adds chromatic aberration** and is on only for the Notes pill. Two halves, because each alone fails somewhere: in the filter, R, G and B are displaced by three amounts (blue furthest) and added back, so content under the rim fringes red outside and cyan inside (Chromium only, and invisible over a plain page); and a drawn iridescent band, magenta at the edge through blue to cyan, confined to **two tapered crescents** on the top-right and bottom-left (normal angle within a narrow lobe, width and strength both tapering). The first version ringed the whole rim and read as a cheap outline: keep it on the corners.
- **Only Chromium renders SVG filters in backdrop-filter** (Chrome, Edge, Samsung Internet, the Play app). Safari and Firefox accept the syntax and draw nothing, so `userAgentData.brands` decides and they get frosted glass with the same rim, tint and shadow. No feature test can say "renders it". Maps are redrawn when the element settles at a new size; until then the glass goes frosted, because a stale map reads as a hard shift at its old edge. `prefers-reduced-transparency` makes it opaque.
- **Never put `opacity`, `filter`, `mask`, `mix-blend-mode` or `backdrop-filter` on an ancestor of the glass**: they are backdrop roots, and the glass would refract nothing but that ancestor. So a glass modal's dimming is a *sibling* behind it, light and unblurred (the sign-in card in `AuthModal.tsx` is the pattern: scrim at 45% black, not the old 80% + blur), and glass enters with `lg-pop` (a transform), never a fade. The phone menu's overlay is unblurred for the same reason. A glass element that can scroll keeps the scroll on an inner wrapper, or its absolutely placed layers scroll away with the content. The capsule is hidden on a laptop by `md:hidden` on the element, not by index.css, because CDN Tailwind's `.flex` is injected later and wins.
- **Overlays render through `Overlay` (a portal).** `<main>` is `relative z-20`, so a fixed modal inside a tab paints under the z-50 rail and the phone top bar.

## Domain model / usage flow

- **Exam preference** (`JEE` vs `NEET`) is chosen at signup and switchable later; it changes which subjects (`getActiveSubjects`/`getCoreSubjects`/`getCoreQSubjects` in `constants.tsx`) and which syllabus chapter set (`SYLLABUS_DATA[11|12]`) are shown, without deleting the other exam's historical data.
- **Exams and the one-time "Pick your exams" modal.** `AppState.exams` (content/exams.ts) is filled in on load from the stream and class for anyone who never chose, so its presence says nothing about whether the student was asked. `AppState.examsAskedAt` does: stamped by onboarding when it ends (finished or skipped), by Settings → Exam (`setExams`) and by `exams/ExamLaunch.tsx`, and kept as the later of both sides in all three merge paths (`laterStamp`). The modal shows (`showExamLaunch` in App) only to someone past onboarding, synced, with an account or some history on this device, no stamp, and no running session or other full-screen moment; announcements, removal notices, the keep banner, the feedback launcher and the gear queue behind it. It opens on the guessed target, so "Lock it in" alone keeps it, and it has no dismiss. Its fields are the Settings sheet's (`useExamDraft` + `ExamFields` in `exams/ExamSheet.tsx`), which also print each exam's month in the chosen year.
- **Tabs** (`Today`, `Plan`, `Syllabus`, `Streak`, `Mocks`, `Ranks`, `Review`, `Groups`, `Decks`, `Notes`, plus `Admin` for staff only) map to the app's core loops:
  - `Plan` — the whole day on one timeline: study alongside class, meals, the gym and sleep, plus a Colours section for recolouring any non-study activity. Drag to move, drag an edge to resize, tap to edit, one-tap quick-add per activity, a Repeat control (just today / every day / every weekday) on each block, and Start now to put the clock on a study block. Dragging a repeating block asks whether you meant that day or the whole series. Plus a repeating-blocks section and a plan-vs-actual adherence readout that grades study only. See Scheduling above.
  - `Today` — start/stop a study session timer (stopwatch or Pomodoro), log focus quality (1-5) and manual hours, work a **Todo → Doing → Done card board** (drag between columns, per-card colour, optional deadlines), view today's per-subject hour distribution, and expand a collapsed session history. See Task board above.
  - `Syllabus` — per-chapter status cycling (`not_started → in_progress → completed → revision_pending`) across Class 11/12 chapters for the active exam's subjects.
  - `Streak` — current daily-logging streak (`calculateStreak`, held through missed days by firewood; see Firewood below), the firewood bank, progress to the next reward, a Share Your Win action (see Shareable stats), the once-a-day streak moment after the first log (see The streak moment), the reward vault (see Streak rewards below), a 7-day hours bar chart, a monthly heatmap, and (if present) question-practice charts.
  - `Mocks` — the mock test planner/tracker and the error notebook. Plan a mock (paper, syllabus scope, chapters and topics), log the result, see trends split by exam and filtered by scope, and re-attempt saved wrong answers as chapter tests. See Mock tests above. Replaced the Questions tab in the same rail slot; question *data* (`questionTracking`) is untouched and still charted on Streak.
  - `Decks` — spaced-repetition flashcards: personal decks and Alpha-wide ones, import a deck file or make cards with the cloze editor, review in a focused room scheduled by FSRS. Alpha packs (sets of Alpha decks) are taken from the Alpha Packs store, a physical rack you slide, and live in My Alpha. See Alpha Decks above.
  - `Notes` — opt-in (a cover page until turned on), then the student's notebook: nested pages, native equations, chapter mentions, to-dos sent to Today, Markdown import, a glass pill for navigation. Local first in IndexedDB, synced between the student's own devices through Supabase. See Alpha Notes above.
  - `Groups` — study groups: a leaderboard over today/week/month/all time, a persistent chat, and per-group opt-in sharing of hours and today's tasks. Joined by invite link or code. See Groups above.
  - `Review` — the composite "Lock-In Score" (see `calculateLockInScore` in `utils.ts`), aggregate stats (total hours/sessions/avg quality), account/sync controls (sign in/out, "Reset Device"), exam-preference switch, contact links, and a manual log entry form (for backfilling sessions not tracked live via the timer).
- **Sync/account model**: the app is fully usable offline/local-only (`OFFLINE MODE` badge); signing in with Google enables cross-device sync (see Persistence & sync model above). There is no anonymous-to-authenticated data migration beyond the merge-by-id logic already described — signing in on a fresh device pulls cloud state; signing out wipes the local device copy (cloud record is preserved, per the confirm dialog copy).

## Supabase (external, not in this repo)

- Project URL/anon key are hardcoded in `App.tsx` (`SUPABASE_URL`, `SUPABASE_ANON_KEY`) — no `.env`-based Supabase config exists in this repo.
- Single table `user_profiles`: `id` (auth user id, PK), `state` (jsonb serialization of `AppState`), `updated_at`. Realtime is enabled on this table for `UPDATE` events (used for the live cross-device sync channel).
